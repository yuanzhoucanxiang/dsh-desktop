## 〔V1–V9 / G1–G4 漏洞 hunt 与逐一修复〕writing-hardening

- **做了什么**：接 v0.1.41 后续审查，对 writing-mode host 数据层、host HTTP 面、外壳 git 审阅层做了一轮 hunt，
  **13 项缺陷全部实锤复现并全部修复**（V1–V9 共 9 项 + G1–G4 共 4 项）。报告与可复跑探针：

- **最严重一项（P0，已在 v0.1.36–v0.1.41 发布版里）**：`index.js` 的 `readBody` 用 `data += String(chunk)`
  逐 chunk 独立 UTF-8 解码。socket chunk 边界与字符边界无关，三字节汉字被切开时两半各自解码失败成 U+FFFD，
  而 `JSON.parse` 对 U+FFFD 完全合法 —— 于是**正文带着乱码一路静默写进手稿**。
  实测 276KB / 92000 码点中文正文 round-trip 后 7 个 U+FFFD，首个差异在第 21751 字。
  修复后同一探针：生产实现 U+FFFD=0、码点级全等；旧实现对照仍 5 个（机理取证保留在探针里）。
- **其余各项**：V2 配置损坏被当"不存在"→一次只改字号就把库根/伙伴绑定/AI Key 清零；
  V3 协调记录 stale-token 落盘 `phase:null` → 该作品永久 `bad-record` 500 且 `forget --force` 也清不掉；
  V4 残留 `.lock` 让每次草稿保存同步忙等 8038ms 并冻结内核事件循环（`setInterval` 计数 0）；
  V5 移动恢复候选与目标作品无关 → 可把 A 作品草稿导进 B 作品；

## 〔S1–S6 外壳本体漏洞 hunt 与逐一修复〕shell-hardening

- **做了什么**：把猎场从 writing-mode 插件扩到**外壳本体**（main.js / preload.js / renderer / lib / review-bridge），
  **6 项缺陷全部实锤复现并全部修复**。报告与可复跑探针：`docs/audits/shell-hardening/2026-09-21/`。
- **最严重一项（S1，P1）**：`preload.js` 的 `dshShell` 桥是无条件 `exposeInMainWorld` 的，凡带这个 preload 的窗口
  （内核页/设置/启动画面/预览）同权；而主窗口承载内核页面，其主世界跑着第三方插件的 client 代码
  （内置就注入了 better-sidebar / pet / palis-theme-panel）。`shell:notify-command` + `-test` 既不弹确认也不看发送方，
  主进程收到就 `spawn(命令串, { shell:true, detached:true })` —— **零确认拿到本机命令执行**，且写进 settings.json 后
  每个回合结束都重放。外壳对同类风险早有明文策略并逐个收口过（open-file 改 showItemInFolder「不给执行面」、
  quit / restart-kernel / update-install 一律过原生确认框），这个入口是那次收口漏掉的。
  修：新增 `isSettingsSender(event)`（`BrowserWindow.fromWebContents(event.sender) === settingsWin`），
  读/写/试跑三个通道全部按发送方窗口授权；命令变更时过原生确认框并原样展示要执行的命令串；每次变更写审计日志。
- **其余各项**：S2 `shell:plugins-restore` 会 `restartKernel()` 却零确认，等于绕过 `shell:restart-kernel` 的确认门
  （顺带把"因搞崩内核被自动隔离"的插件重新启用）→ 补原生确认，并移除 settings.js 里那个可被页面改写的渲染侧 confirm；
  S3 `{cwd}`/`{workspace}` 裸拼进 `shell:true` 命令串 → 实测工作区名 `ws & node s3-payload.js` 时
  `echo hook {cwd}` 真的执行了 & 后面的载荷 → 抽出 `lib/shell-quote.js` 按平台加引号，安全路径**原样返回**不引入回归；
  S4 `setEntryDisabled` 把 entry id 原样插值进 `- id: ${id}` → 实测含换行的 id 能把 `- id: hijacked` +
  `name: '@attacker/pkg'` 写进决定内核加载什么的 profile 补丁 → 加白名单校验，不符即拒写；
  S5 `/api/review-bridge/revert` 请求体无上限（同仓库 writing-mode 早已限 1 MiB，自家口径不一致）→ 补 1 MiB + 413；
  S6 `readSessionChanges` 每次刷新整份读 + 逐行 parse + 全量过 IPC，而流里每条 write 都带 `new:<整个文件内容>`
  （实测 20 次 400KB 写入 = 7.8MB 流、每次刷新搬 7.8MB）→ 抽出 `lib/ndjson-tail.js` 只读尾部（4 MiB / 2000 条双闸），
  截断时侧栏用 textContent 如实告知并指路 Git 视图。**尾部截断安全**：逐条回退不依赖这份流（bridge 用自己内存里的 session events 查 callId）。
- **改动文件**：新增 `lib/shell-quote.js`、`lib/ndjson-tail.js`、`lib/shell-hardening.test.js`（39 项）；

  release.ps1 / prepare-runtime.ps1 / install-update.ps1 / gen-update-manifest.js /
  main.js 的更新源与更新器缓存逻辑。5 项缺陷全部实锤复现并全部修复。
- **威胁模型的定位**：这条链上没有远程攻击者（更新源不可由渲染侧改写，见下"查过干净"）。
  真正的风险是**发布/维护流程自己**在陈旧或不一致的输入上做出不可逆动作且事后不报警——
  那些动作是"强杀正在运行的应用然后静默安装"或"把清单推给全量自动更新客户端"。
- **U1（P2）**：install-update.ps1 无参数时按 LastWriteTime 挑安装包，不解析版本、不校验 sha512、
  无降级防护；而它动作前先强杀桌面与内核。实证：本机 ~/Downloads + dist 共 20 个候选，
  会挑中 dsh-desktop-0.1.37-setup.exe，而 package.json 是 0.1.41 → 静默装落后 4 个版本的包，
  事后只在"版本没变"时给 WARNING，降级不报。修复：按版本降序选包（解析不出的候选跳过）、
  旁边有 latest.yml 就校验 version + sha512(base64) + size、比已装版本旧默认拒绝（需 -Force）；
  三项检查全部前移到杀进程之前。
- **U2（P3）**：killStaleUpdaterInstallers() 把 LOCALAPPDATA 派生路径裸拼进 PowerShell 单引号串，
  紧邻 Stop-Process -Force 管道。实证：路径含单引号时拼出的命令串单引号数为 5（奇数=未闭合）。
  修复：改走 $env:DSH_UPDATER_DIR 传值、零拼接，并加变量非空判断（避免 StartsWith($null) 匹配一切）。
- **U3（P3，缺闸门而非已漂移）**：owner/repo 在 5 处硬编码（package.json build.publish、
  main.js DEFAULT_UPDATE_REPO、build.ps1 的 app-update.yml heredoc、release.ps1、install-update.ps1），
  updaterCacheDirName 另在 3 处；当前取值一致纯属巧合，改任一处无检查报错。
  修复：build.ps1 改为**从 package.json build.publish 派生**（消除一处硬编码），
  新闸门比对全部来源、含 --dir 指定的解包产物里真正生效的 resources/app-update.yml。
- **U4（P2，发布路径）**：发布前零一致性校验，而 release.ps1 未认证分支会把 gh release upload
  命令打印出来让人手工执行。实证：本机 dist/latest.yml 是 0.1.37（自身自洽：sha512/size 与
  0.1.37 的 exe 实算一致），但整份指向 4 个版本前；另有 2 个孤儿 blockmap、遗留 win-unpacked.tmp、
  20 个历史包共 3.9GB。修复：新增 scripts/verify-release-artifacts.mjs，接进 build.ps1 步骤 5b
  与 release.ps1 步骤 1b。硬失败项：版本不符 / path-url 不指本轮包 / exe 缺失 / sha512-size 与实算不符 /
  本轮 blockmap 缺失 / 更新源或缓存目录名漂移 / .ps1 非 ASCII 或不可解析。卫生问题只警告不失败
  （当硬门禁会让 npm run dist 在无关陈旧文件上挂掉）。
- **U5（P3，哑弹）**：build.ps1 有 2 行中文注释（v0.1.31 / commit 31f5943 引入）、
  prepare-runtime.ps1 有 1 行且未声明 ASCII-only 规则，而 build.ps1 头部明文记过真实事故
  （"This actually bit us: adding Chinese comments here produced 'Unexpected token' and the build died"）。
  至今碰巧能解析。修复：全改 ASCII + 补声明；闸门对四个 .ps1 断言零非 ASCII 字节 +
  能被 System.Management.Automation.Language.Parser 解析（只解析不执行）。
- **查过判定干净的（不报，避免噪音）**：① settings.updateRepo / updateUrl **没有任何 IPC 通道**，
  渲染侧只能写 panelWidth（夹取 320–800）与 notifyCommand（已按 S1 授权+确认），其余走托盘/菜单原生 UI；
  ② release.ps1 的 $owner/$repo 硬编码、不读 settings，发布目标不可被配置重定向；
  ③ renderUpdateNotes() 全过 esc() 且不生成任何 href，所以"feed 可控文本 → 设置窗口 XSS →
  借用 S1 信任的发送方身份"这条链不成立（这条特意查过，因为设置窗口现在是授权闸信任的发送方）；
  ④ gen-update-manifest.js 的 sha512(base64)/size 口径正确、日志走 stderr（08-25 那次实故已修好没回退）；
  ⑤ build.ps1 的 $LASTEXITCODE 纪律完好（每个 native 步骤都查，NSIS 前先删同版本包）；
  ⑥ install-update.ps1 的进程清理范围克制（只碰安装目录下的 node.exe 与更新器缓存目录下的安装器）。
- **我自己引入并修好的回归（W23，门禁抓到的）**：全量 20 步门禁里 test:writing-world 非零，
  逐段定位到 world-settings-p3.mjs 的 FAIL W23 live lock not stolen（错误码 lock-stale，
  断言只接受 lock-timeout / lock-failed / null），连跑 3 次 1 红 2 绿。根因：上一轮 V4 把
  "陈旧锁快速失败"从等满 8s 收到 250–400ms，却沿用 !isOwnerAlive(owner) 判死，把三种状态压成一种——
  ① 锁刚被释放（应立即重试获取）② 对方已 openSync('wx') 未 writeSync 的空文件（是活锁）
  ③ 令牌可解析且 PID 已消失（才是陈旧锁）。W23 子进程持锁 2.5s 后 unlink，父进程若正好在
  tryAcquire() 拿到 EEXIST 之后、readLockOwner() 之前撞上这次 unlink 就读到空串 → 判死 →
  400ms 阈值早已过 → 抛 lock-stale。**旧代码同样误判，但陈旧分支要等满 8s，下一轮 tryAcquire() 就成功，
  所以从未暴露——我缩短 deadline 等于把一颗一直存在的哑弹点了火。** 修复：新增 ownerIsProvablyDead()
  （必须能解析出 PID 且该 PID 确实不存在）、获取循环先判锁文件不存在就 continue、读不出持有者一律按
  活锁预算等；inspectLock() 增 dead 字段，quarantineStaleLock() 与两处启动清扫改为只认 dead
  （否则空锁文件会被改名隔离，那是真会丢数据的路径）。钉住：hardening-v1-v9.mjs 加 11 条断言
  （含真子进程持锁→unlink 的 6 轮并发复现，要求 lock-stale 计数为 0），66 → 77 项全过；
  world-settings-p3 连跑 6 次 W23 全绿、test:writing-world 连跑 3/3。
- **验收**：探针重跑 0/4；verify:release-artifacts --allow-stale → RELEASE_ARTIFACTS_OK；
  默认严格模式 exit 1 且如实报出 dist/latest.yml 落后 4 个版本（闸门在履职，不是闸门坏了）；
  四个 .ps1 均 ASCII 字节 0、解析器语法错误 0；全量 Node 门禁 20 步，非零 1 步（即上面那条如实报告）。
- **改动文件**：新增 scripts/verify-release-artifacts.mjs、docs/audits/release-chain-hardening/2026-09-21/{report.md,hunt-release.mjs}；
  改 install-update.ps1、main.js、build.ps1、release.ps1、prepare-runtime.ps1、package.json、
  plugin/writing-mode/lib/{file-lock,draft-checkpoints,coordination}.js、plugin/writing-mode/test/hardening-v1-v9.mjs。
- **仍未做（如实标注）**：NSIS 安装向导/注册表、macOS 实机（build-macos.sh / update-macos.sh 未纳入本轮）、
  受控离线、真实模型场景；本轮真包验收都是 dir 目标，**app-update.yml 的派生逻辑与 5b 闸门未在 NSIS 全流程里跑过**；
  install-update.ps1 的 sha512 校验依赖"包旁边有 latest.yml"，-Download 落到 %TEMP% 时只提示跳过而不失败（未闭环）。
- **坑 / 备注（两条，都值得记）**：
  ① **编辑工具会把 Windows 路径里的反斜杠当转义吃掉**：我往 build.ps1 写 `"$proj\gen-update-manifest.js"`，
     落地成了 `"$projgen-update-manifest.js"`（`\g` `\s` `\d` `\r` 全被吞），把构建脚本改坏了。
     修法：改 PowerShell 脚本里的路径一律用**正斜杠**（PS 与 node 与 .NET 在 Windows 上都接受）或 Join-Path，
     且 SearchReplace 的 original_text 锚点要**避开含反斜杠的行**。发现后立刻读回真实内容修好了。
  ② **PowerShell 的 -Filter 不支持 `[67]` 这类括号字符集**：我用 `Get-ChildItem dist -Filter "*0.1.3[67]*"`
     得到空结果，一度以为 0.1.37 的安装包不见了；改用 node 逐条 readdir 才发现文件一直在。
     下结论前必须换一种方式复核，不能凭一次过滤的空结果报"文件缺失"。
