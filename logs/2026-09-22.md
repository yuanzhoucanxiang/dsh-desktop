- **CXR01（P1）锁清扫能移走活锁 → 在线一律不再移动他人的锁。**
  复核的反驳成立：check-then-rename 无法原子化，我上一轮加的"改名前第二次复核"消除不了双持有窗口；
  而且我注释里写的"revision/etag 会兜底"也是错的——它们是临界区**内部**的读后比较，
  前提是互斥已成立，互斥失效后不会自动变成 CAS。已把这段错误论证从注释里删掉并改写成复核的时序。
  具体改动：
  - `quarantineStaleLock(file, opts)` **必须显式传 `{ offline: true }`** 才动作，否则直接返回 null；
    仅供"应用已关闭、确认没有写入者"的离线维护使用。
  - `sweepStaleDraftLocks()` / `sweepStaleCoordinationLocks()`（会移动）**删除**，
    改为只读的 `listStaleDraftLocks()` / `listStaleCoordinationLocks()`；
    两个文件不再 import `quarantineStaleLock`。
  - `index.js` 内核启动路径改为**只诊断**：把残留锁的绝对路径打进 warn 日志，不动文件。
  - 维护接口 `POST maintenance {action:'clear-stale-locks'}` 改为 **409 拒绝**
    （`stale-lock-clear-refused-online`），返回 `stale` 列表 + `instruction`（关应用后手动删哪些文件）；
    理由：该接口跑在内核里，"没有任何写入者"无法被证明。
  - 锁诊断行新增 `path`（锁文件绝对路径）；`lock-stale` 错误新增 `lockPath` / `lockOwner`，让诊断可操作。
  - **代价（如实记）**：崩溃留下的残留锁现在会一直卡着那个桶（每次保存快速报 lock-stale）
    直到作者关掉应用手动删除。这是故意取舍：宁可一个桶暂时不可写，也不要两个写入方重叠造成静默覆写。

- **CXR02（P1）同名稿件被当成同一作品证据 → 降级为提示。**
  `relocationRelation` 里的 `manuscript-reference` 分支（同相对路径文件存在即 importable=true）**移除**。
  现在证据只有两种：`memory-project-key`（备忘里记过旧路径）、`projection-record`（可读稿抬头记过旧路径）。
  同相对路径的观察改为 `relation='unrelated-filename-hint'`、**importable 永远 false**，
  detail 明说"文件名相同不等于同一部作品，这不构成关联证据"。
  内容指纹同理：拿草稿里的引用快照与目标文件比对，一致也只写进 detail 当**辅助线索**，不授予导入资格。
  客户端一并改：面板说明不再把"同名同位"列为证据并明说它不算证据；
  确认框按裁决 1 **同时显示来源（旧位置）与目的（当前作品）**，不再只说"当前作品"。
  显式知情覆盖（`confirmUnrelated === true`）与审计留痕（`unrelated-author-confirmed` 写进历史桶）保持不变。

- **裁决 3 第三条：未知 owner 不当死锁，但也不白等 8s。**
  `withFileLock` 现在有三种等待预算对应三种状态：活的持有者 → `deadlineMs`(8000) 报 `lock-timeout`；
  可证明已死 → `staleFastFailMs`(400) 报 `lock-stale`；读不出持有者 → `unknownOwnerFastFailMs`(800)
  报新错误码 **`lock-owner-unknown`**（可重试，带 lockPath/lockOwner）。
  垃圾内容的锁文件不再让每次写入白等 8 秒。
  **差点重演 W23**：新分支最初没有"放弃前再确认锁是否已消失"，那么
  `existsSync 为真 → 文件被释放 → readLockOwner 拿到空串` 就会把一个本该成功的获取变成硬失败
  （与 W23 同一形状、只是错误码不同）。在跑测试**之前**推演发现并补上 `if (!fs.existsSync(lock)) continue`，
  并加了源码形状断言钉住，防止后人删掉这一行。
