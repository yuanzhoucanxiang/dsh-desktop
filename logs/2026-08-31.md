# 2026-08-31

## 〔99〕 侧栏 Markdown 链接 XSS + 窗口导航守卫收口 + 未跟踪文件还原失效（v0.1.30）

#### 1. 审阅侧栏 Markdown 链接 XSS（高危）

审阅侧栏的文件查看器会把 .md 渲染成链接：`mdInline` 把 markdown 链接
直接赋给 `a.href`（preload.js）。渲染内容来自**工作区内的被审阅文件**——
恶意 README 写 `[x](javascript:...)`，用户点开即在该内核页面上下文执行
脚本（页面带着 `window.dshShell` 全量 IPC：读任意工作区文件、开文件、
改插件开关、提交/推送、装更新）。翻检查明：侧栏 DOM 全用 textContent/
createElement（无 innerHTML），这是唯一一处把不可信输入喂给 href 的坑。
修：链接只放行 `http/https/mailto`，其它协议降级为纯文本（span + 提示）。

#### 2. 窗口导航守卫收口（高危，四窗口缺三）

preload 在每个 BrowserWindow 每次导航后都会重新注入 `dshShell`，所以
"窗口能导航到哪"就是 IPC 的边界：

- 主窗口 will-navigate 对 `file://` **无条件放行**——历史遗留，程序性
  loadFile(SPLASH) 根本不走 will-navigate，这条白名单没有正当需求；
  放行意味着把窗口导航到任意本地 HTML（如工作区被植入的文件）即拿到 IPC。
- 额外窗口（Ctrl+Shift+N，openExtraWindow）**完全没有 will-navigate**。
- 设置窗口（openSettingsPanel）/ 启动画面预览窗口（openPreviewWindow）
  也没有 will-navigate。

修：统一 `hardenWindow(w, { allowLocal })` —— setWindowOpenHandler
（http/https 转系统浏览器、其余丢弃）+ will-navigate（内核页同源才放行；
本地页额外放行**应用目录内**的 file://，用 app.getAppPath() + fileURLToPath
+ path.relative 判定）。四个窗口全部套用。origin 级比较沿用上轮修法
（startsWith 前缀匹配会被 127.0.0.1:3690.evil.com 绕过）。

#### 3. 未跟踪文件「还原」静默失效（功能 bug）

shell:revert 把 workspacePath 解析后的**绝对路径**传给
review.revertFile；git-review.js 的 untracked 分支又对它
`path.join(getCwd(), file)`——path.join 遇绝对路径不重置，拼成
`C:\...\web\E:\Deepseek\...` 畸形路径，rmSync 永远失败，而 IPC 层把
布尔 ok 直接吞掉（UI 只 refresh 不提示）。安全性上无害（打不到工作区外），
但"删除未跟踪新文件"按钮是个死按钮。
修：`path.isAbsolute(file) ? file : path.join(getCwd(), file)`，并在
git-review.test.js 补绝对路径删除回归用例（相对路径用例已有）。

#### 排查过但确认无风险的

- review-bridge 事件流逐行 `JSON.stringify(obj) + '\n'`（plugin/review-bridge.js:193）
  ——换行/特殊字符被 JSON 转义，不存在 NDJSON 逃逸。
- palis applyAttributes 只写归一化后的常量（on/off、枚举），无注入面。
- settings.js 的内联 HTML 全部走 `esc()`（插件名、版本、错误消息），无 XSS。
- git 操作全部 execFileSync 参数数组（无 shell），路径带 `--` 分隔符；
  git-commit 的消息走 `-m` 参数，无命令注入；push 有确认对话框。
- workspacePath 仍是词法包含判断（与 review-bridge withinCwd 一致）：
  加 realpath 会误伤链接农场（node_modules/@deepseek-ai → 运行时），
  收益有限，仅记录在案。
