# 第二轮（同日）：继续查漏补缺——转向**动态行为**

## 换了个方向

上一轮查的是「文档 ↔ 代码」的**静态**对照。这一轮专查**动态行为**：跨窗口、退出路径、重启、层级。
静态对照永远看不到这些，因为它们不在任何一个函数里，而在**两个状态之间的跃迁**上。

## 新找到的问题

### D4 · `Esc` 是一条绕过关闭守卫的退出路径（新缺陷）

宽窗主屏的 `onKeyDown`：

```js
if (event.key === 'Escape') { setOpen(false); return }
```

而正规出口 `exitWorkbench()` 是：

```js
await collapseSplice()
if (active) { const r = await exitMode(registry); if (!r.ok) return }
setOpen(false)
```

`exitMode` 会先问 `canDeactivate`。**所以有未保存稿时按 `Esc`，守卫根本没被问，工作台直接关了。**
更别扭的是：**小条下的 `Esc` 走的是 `exitWorkbench`（对的）**，宽窗主屏下的 `Esc` 只关主屏——
同一个键在两种形态下语义不一致。门面的 `spliced` 状态也因此不清（壳在 `normal` 时会收掉窗口，两边对不上）。

### 通知 toast 会被模式浮层盖住（新问题）

- toast `z-index: 1410`；写作浮层 **2000**、坞 **2100**。
- toast 挂在 `.dshWbHome` 里当子节点 ⇒ **主屏开着**时它画在主屏（2200）之上，看得见 ✅
- 但主屏**关着**时 `Chrome` 只返回 toast 片段 ⇒ 没有任何更高的父节点 ⇒ **被模式浮层盖住** ❌
- 而交接提示恰好发生在这时：**交接 = 切到目标模式 ⇒ 主屏已经关了 + 目标浮层在场**。
  用户看不到"已把引用交给 GIR"这句话。
- **为什么门禁一直是绿的**：探针只判 `[data-wb-notice]` **存在**与文案，
  从没判过 `getComputedStyle` 的可见性/层级。这是"弱断言"的典型——存在 ≠ 看得见。

### 三处流程事实写错了 / 没写

1. **流程 4 原来写着"主屏留在后面不卸载"——错的。** `switchMode()` 成功后就 `setOpen(false)`，
   主屏渲染 `null`、窗口申请 `normal`，**长条也一起没了**。
2. **模式浮层盖满整屏 ⇒ 侧栏「工作台」入口点不到**；而且**退出模式后回的是内核界面、工作台不会自动重开**
   （全库只有 `setOpen(false)`，**没有一次 `setOpen(true)`** 除了入口点击）。
   也就是说"进模式 → 出模式"是一趟**回不到工作台**的路。
3. **重启会自动进上次的模式**：`adopt(activeModeId)` → `onActivate({reason:'restore'})` ⇒
   上次停在写作模式，下次开应用**直接满屏写作台**。文档从没写过，用户会以为应用坏了。

## 方法论再沉淀一条

**静态对照查"写错了"，动态对照查"根本没写"。** 这轮四条里有三条（D4、toast、进出模式）
都属于"两个状态之间的跃迁"，在任何单个函数里都读不出来——必须追问：
**这个动作之后，另一个状态会变成什么？谁负责清理？用户此刻看得见什么？**
具体可复用的三问：① 这个出口和那个出口，清理动作一样吗？
② 这个提示出现时，屏幕上还有谁压着它？
③ 这个状态重启后还在吗？在的话用户会看到什么？
