## 〔104〕 内核接触面契约 + 可执行验收套件（用户「我要收益最长远的」）

#### 动机

内核升级的适配成本几乎全在「发现晚 + 归属慢 + 修法散」：0.1.2 那次是你肉眼发现
变形、我们猜了若干轮才定位到内核、修完还连做四版主题硬化。三项里只有第三项能靠
重构缓解，前两项只能靠**把依赖变成可执行的契约**——这是唯一会随每次内核升级复利
的资产（每加一条探针就永久多一层保护），也是适配器/隔离/流程的下游依据。

#### 交付

- `contracts/kernel-surface.json`：17 条接触面逐条声明 what / expect / probe /
  fallback / severity。覆盖外壳 12 条（运行时布局、runtime marker、启动行与 token、
  CLI+补丁启动、就绪码集合、/api 鉴权链、profile 清单 schema、bundle 声明、
  插件裸路由、补丁热重载语义、settings RPC、日志编码）与主题 5 条（设计令牌、
  模块加载器、DOM 锚点 12 个、slots API、渲染不变量 4 项）。
- `scripts/verify-kernel-contract.mjs` + `npm run verify:kernel`：Hermetic 验收
  （独立 `DSH_HOME` 临时目录 + 随机端口 + `--keep`/`--json`/`--timeout`），
  拉起真内核逐条探针，打印 PASS/WARN/FAIL/SKIP 报告，critical 失败退出码 1
  （即 CI 兼容门的判定依据）。**pending 行显式报「未接入」，绝不当通过。**
- 基线：`contracts/baselines/0.1.1-rc.1.json`（首跑结果存档，供将来 diff）。

#### 首跑基线（当前内核 0.1.1-rc.1）

13 通过 / 0 critical 失败 / 5 条未接入。要点：
- 启动行可解析（本世代无 token）、补丁内 file:// 插件行被加载、就绪码 200、
  `/api` 未启用鉴权、review-bridge 裸路由应答 409、空 home 内核自愈初始化清单。
- 主题静态探针：设计令牌 13 项命中、`__ModuleLoader__` 命中、**DOM 锚点 12 项
  在 101 个内核客户端产物文件里全部命中**——锚点分布确认在
  `@deepseek-ai/dsh-client-ui-*/lib/*.js`，所以改名可静态检出，不必等浏览器。
- `env.installed-plugins`：本机已装 5 个插件（super-injector / palis-theme-panel /
  auto-mode / better-sidebar / dsh-pet）全部可加载。

#### 实现中值得记的坑

- **stdout 必须按行装配**：套件自己就栽在这上面——直接对 chunk 跑正则时，
  `dsh-client-ui-*/lib/*.js` 这种注释里的 `*/` 会提前闭合块注释（JS 语法错），
  而真问题在语义上：启动行跨 chunk 分片会解析失败。外壳的 `captureWebUrl`
  正是这个写法（已知隐患，见〔103〕讨论），套件里做对了才能真实复现该探针。
- **内核自带 bundle 要从插件体检里排除**：`@deepseek-ai/dsh-base` / `dsh-web-app`
  由内核从运行时目录解析、不在 profile 的 node_modules 里，误检会全红。
  顺手把这份名单收成单一来源（`lib/profile-inspect.js` 导出 `CORE_BUNDLES`，
  main.js 与套件共用），避免三处各写一份而漂移。
- 空 home 的插件检查是空转的，所以另加 `env.installed-plugins` 只读检查真实
  profile——那才是内核升级时真正会坏的东西。

#### 维护约定（写在契约文件头部）

新增任何对内核的依赖（新锚点/令牌/API/启动行字段/文件布局）时同一条 PR 里补一行；
内核升级后跑 `npm run verify:kernel`，红项按 probe 名定位到本表再改代码。
5 条待接入探针（补丁热重载语义 / settings RPC / 日志编码 / slots API /
**渲染不变量**）——最后一条需要 CDP 实时渲染层（LayerTree 快照 + 逐帧圆度 +
DPR 2.73 仿真），是下一步的主要工作。

署名：ox-alpha

## 〔105〕 渲染不变量探针（契约 theme.render-invariants 接入）

#### 为什么单独一个脚本

其余契约探针是协议/文件级的（秒级、无浏览器）；这一条必须**真起浏览器 + 真渲染 +
逐帧采样**，才看得见「静态截图看不出来」的那类破坏——0.1.2 内核那次球体/月面/
声纳变形正是这一类（DOM 契约全中、截图逐像素是正圆，只有实时合成路径可见）。

`scripts/verify-render-invariants.mjs`（`npm run verify:render`，或
`verify:kernel --render` 由套件代为执行并汇总）。Hermetic：临时 `DSH_HOME` +
junction 挂入主题插件（与真实 profile 同构）+ 随机端口 + 临时 Chrome profile，
绝不碰用户实例。步骤：起内核 → `POST /api/palis-theme {theme:'palis'}` 打开主题 →
headless Chrome 以 **DPR 2.73 仿真**（复现本机环境）导航 → 等装饰层挂载 →
逐帧采样 40 帧 + LayerTree。

#### 四项不变量与实测（内核 0.1.1-rc.1，全绿）

| 探针 | 检查内容 | 结果 |
| --- | --- | --- |
| render.containing-block | 装饰层祖先链上不得有 transform/filter/backdrop-filter/perspective/will-change/contain（**根因检查**：这些一出现，absolute 层改按新包含块解析、fixed 层被捕获） | 7 个元素祖先链干净 |
| render.viewport-anchor | 每个 fixed 装饰层须横向通栏 + 垂直贴顶或贴底 | 全部严丝合缝 |
| render.circle-aspect | 圆形元素 40 帧内宽高恒等（=拉伸的直接判据） | 全部恒等 |
| render.dpr / render.compositing | DPR 仿真生效；合成层数与非常规 transform | 生效；LayerTree 无头下上报不稳，保持 warn 级不参与判定 |

#### 过程中的两个教训

- **探针的断言本身会错**：首跑 `.palis-statusbar` 报 FAIL——它是底部状态条（贴底、
  通栏），我却按"满屏层"要求它。判据改成「横向通栏 + 贴顶或贴底」才对。记录下来：
  这种验收套件的红项要先问"是产品坏了还是断言写错了"。
- **无头模式的 LayerTree 不可靠**（两次跑一次报 4 层、一次不报），所以合成层检查
  定为 warn 级、不进 critical 判定；真正的不变量判定靠几何采样（确定性强）。

#### 一条命令的全貌

`npm run verify:kernel --render` → 14 项通过 / 0 critical 失败 / 4 条待接入
（补丁热重载语义、settings RPC、日志编码、slots API）。基线存
`contracts/baselines/0.1.1-rc.1.json` 与 `contracts/baselines/render-0.1.1-rc.1.json`。

署名：ox-alpha

## 〔106〕 官方新内核 0.1.5-rc.1 契约验收（用户「官方现在的新内核就有更新了」）

#### 结论先行

官方 `latest` 已到 **0.1.5-rc.1**，我们钉在 0.1.1-rc.1（差 0.1.2/0.1.3/0.1.5 三条线）。
在候选内核上跑契约验收后，三件事定了：

1. **外壳不需要改代码**：0.1.5 的 token 鉴权链与 0.1.33 的适配完全对得上——
   启动行带 token（stdout，可解析）、`/` 返回 401（`probeReady` 接受）、
   `/api` 无 cookie 401 → 换 cookie → 重试通过。0.1.2 那轮保留的适配直接复用了。
2. **主题要改两条选择器**：输入区被重构，`data-input-mirror` / `data-input-backdrop`
   没了，改成 `data-composer-*` 家族（input/placeholder/text-ref/stats/chip）。
   主题里正好两条规则用它们（输入框底色 `#0a0a0a` 与文字色/text-fill-color）。
3. **渲染变形回归已修复**：四项不变量在 0.1.5 上全绿（含 DPR 2.73 下 40 帧圆形恒等、
   祖先链无包含块）——0.1.2 让我们回退的那个问题，0.1.5 不复现。

#### 最重要的发现：升级不是"换 runtime"，而是"刷新插件树"

隔离预览（dev runtime 临时指向候选）**启动失败**：

```
failed to import loader entry subagent-model-selection-settings
(@deepseek-ai/dsh-tool-subagent/model-selection-settings): Package subpath
'./model-selection-settings' is not defined by "exports" in
C:\Users\DL\.dsh\profiles\web\node_modules\@deepseek-ai\dsh-tool-subagent\package.json
```

根因：装插件时 pnpm 把内核包按当时的版本解析进了 profile
（`profiles/web/node_modules/@deepseek-ai/*`，共 **197 个，全是 0.1.1 世代**）。
新内核会生成引用"新版才有的子路径导出"的 loader entry，撞上这些旧副本即崩。
**新装环境无此问题**（所以空 home 的契约验收全绿），只有既存 profile 会踩。

这解释了为什么"契约套件全绿"与"真机起不来"能同时成立——两者用的 home 不同。
已把它做成契约行 `shell.profile-kernel-packages`（critical）：比对 profile 副本与
内核的数字三元组，跨版本即红。**实测：对 0.1.1 通过、对 0.1.5 候选准确报红**
（193 个包不同族，如 cordis 4.0.1 vs 4.0.2）。

#### 随之新增的升级入口

- `scripts/prepare-candidate-runtime.mjs`：把任意内核版本装成候选运行时到工作区外
  （`--version 0.1.5-rc.1 --registry …`），不动已安装实例。
- `verify:kernel --runtime <dir>`：在候选上跑全套契约（`--render` 一并跑渲染探针）。

#### 检测器自身的三处缺陷（都被这轮实测逮到）

1. **就绪语义**：原实现"任何应答即就绪"，而 0.1.5 的端口会先答 404、约 1s 后才转
   401 并打印启动行 → 误判就绪并漏掉启动行。改为只认 200/401/303（与外壳 probeReady
   同语义）+ 启动行宽限期 + stderr 诊断（若启动行跑到 stderr，外壳读不到）。
2. **渲染脚本未适配鉴权**：拿裸 URL 导航 → 浏览器停在 401 页 → 装饰层永远挂不上。
   改为解析启动行、按带 token 地址加载（与外壳 `kernelPageUrl()` 同）。
3. **探针刻度写错**：新契约行首版按 `major.minor` 比对，把 0.1.1 与 0.1.5 折叠成同一个
   "0.1" 而漏报；改为数字三元组。教训同〔105〕：红/绿都要先问"是产品还是断言"。

#### 现场状态

dev runtime 的临时指向已恢复（回到 0.1.1-rc.1），预览实例未能启动（上述 profile
陈旧问题）故未保留运行；`runtime.bak-0.1.1` 已改回 `runtime`。

#### 建议的升级路径

① 改主题两条选择器（`data-input-*` → `data-composer-*`）→ ② 针对 0.1.5 刷新插件树
（重新解析插件依赖，让 profile 的 `@deepseek-ai/*` 跟上新内核；注意 pnpm 跨盘 link
会悬空的旧坑）→ ③ 契约套件 + 渲染探针复跑全绿 → ④ 隔离实例目检（变形、输入框、
四个内置插件）→ ⑤ 采纳：`prepare-runtime` 版本钉 0.1.5-rc.1、重建发行版、走预发布。

署名：ox-alpha

## 〔107〕 主题输入区双写 + 契约 either/or（0.1.5 升级准备，前半）

#### 做了什么

1. **主题双写（palis 0.5.8）**：0.1.5 把输入区从 `<textarea>` 重构成
   `div[contenteditable][role=textbox]`。映射不是猜的——用 Hermetic 起内核 +
   headless Chrome 取**实时 DOM 锚点清单**，新旧两代对比得出：
   `data-input-backdrop → data-composer-input`、`data-input-mirror → data-composer-placeholder`、
   `[data-composer-seat] textarea → [data-composer-input]`。三条规则并列新旧选择器：
   只改新选择器会让 0.1.1 用户立刻失去输入框主题化（版本绑定），双写则两代同吃一份 CSS，
   主题因此与内核版本解耦、可独立发布。
2. **契约锚点行改 either/or 语义**：双写组任一存在即通过（`detail.eitherOr`），
   否则 0.1.5 上会因旧锚点消失而误报红。两代内核各跑一遍：均 12 项全命中。
3. **渲染探针新增 `render.composer-theme`**：直接量写作区计算样式，两代内核都命中
   PALIS 底色 `rgb(10,10,10)` 与 JetBrains Mono——这条就是双写的回归闸。
4. **渲染探针新增 `--shot`** 目检留证（截图存 verify-out/）。

#### 本轮又逮到一处探针盲区

`circle-aspect` 只量包围盒宽高恒等（**拉伸**），量不出**圆角被改**。0.1.5 上开机自检舷窗
`.pb-port` 的截图看着像"圆角方"（squircle，非正圆）——旧内核同位置截图也裁在视口外难比对，
本轮未定性。这是"截图看着不对但不变量全绿"的第一例，已记在案；若确属内核侧合成/圆角问题，
是 0.1.2 那类问题的近亲（需要 LayerTree + 圆角几何两类探针同时看）。

另：Hermetic 全新 home 首启会弹"内测声明"模态，干净截图需要先关掉它（本轮截图因此被挡，
判定改用计算样式绕开）。这是验收环境要处理的下一个细节。

#### 0.1.5 升级现状：只剩一处拦路

契约套件对 0.1.5 候选的结论：**外壳零改动**（token 链三项全通）、**主题已适配**（双写）、
**渲染不变量全绿**；唯一红项是 `shell.profile-kernel-packages`——profile 里 197 个内核包
副本全是 0.1.1 世代，新内核生成的 loader entry 引用新子路径导出即崩。即下一件事：
把"刷新插件树"做成可回滚能力。

## 〔108〕 纠正〔106〕的结论：「刷新插件树」不必要——链接跟随运行时路径

#### 实测推翻

〔106〕判定"升级内核必须刷新 profile 里的内核包副本，否则启动即崩"。开挖第二件
（把刷新做成可回滚能力）时先看清现场，发现**前提就是错的**：

- `profiles/web/node_modules/@deepseek-ai/*` 的 199 个条目**不是陈旧副本，是符号链接**
  （目录总大小 821K、`.pnpm` 为空），指向
  `%LOCALAPPDATA%/DeepSeek Harness Desktop/runtime/node_modules/@deepseek-ai/*`。
- 内核的 `healProfilesModuleFallback` 只维护 `profiles/node_modules`（共享层）；
  web profile 里这些链接指向"安装版运行时路径"。

于是做了「同路径换内容」模拟（临时 home + 稳定路径 rt，web 链接指向 rt）：

| 场景 | 结果 |
| --- | --- |
| ① rt = 0.1.1（升级前） | BOOT_OK |
| ② **rt 原地换成 0.1.5** | **BOOT_OK**（401 = 0.1.5 在跑） |
| ③ 链接指 0.1.1 路径、却从候选目录起内核 | BOOT_FAIL，复现同一条 `failed to import loader entry subagent-model-selection-…` |

结论：
- **安装版升级是安全的**——运行时在同一条路径上被原地替换，profile 的链接跟着路径走，
  不存在版本错配。②证明了这一点。
- 〔106〕看到的崩溃是**dev 预览的错配**（我从 dev 目录起候选内核，而链接指向安装版运行时），
  ③复现了它。不是升级风险，是我的验证姿势不对。

#### 因此

- **「刷新插件树」这项工程取消**（不需要）。契约行 `shell.profile-kernel-packages` 由
  critical 降为 warn，并把语义改写成"链接与本轮被测内核不同源"——它现在的用途是提醒
  "你在用另一个目录的运行时做验证"，而不是报警升级有风险。
- **候选预览的正确姿势**：用独立 `DSH_HOME`（全新 profile 的链接由内核指向它实际使用的
  运行时，自然同源）。这也解释了为什么契约套件/渲染探针在一路 0.1.5 上都全绿——它们用的
  是新 home。共享 profile 上硬跑候选会撞 ③。
- 教训归档：**"契约套件全绿 + 真机起不来"出现时，第一件事是问两者的 home/运行时是否同源**，
  而不是假定产品有缺陷。这次差点据此造一个不必要的风险工具。

#### 0.1.5 升级现状（修正后）

外壳零改动、主题已双写适配、渲染不变量全绿、**无需刷新插件树**。剩下的只是常规动作：
把 `prepare-runtime` 的版本钉到 0.1.5-rc.1 → 重建 dist → 独立实例目检 → 走预发布。

署名：ox-alpha
