## 〔104〕 内核接触面契约 + 可执行验收套件（用户「我要收益最长远的」）

#### 动机

内核升级的适配成本几乎全在「发现晚 + 归属慢 + 修法散」：0.1.2 那次是你肉眼发现
变形、我们猜了若干轮才定位到内核、修完还连做四版主题硬化。三项里只有第三项能靠
重构缓解，前两项只能靠**把依赖变成可执行的契约**——这是唯一会随每次内核升级复利
的资产（每加一条探针就永久多一层保护），也是适配器/隔离/流程的下游依据。

#### 交付

- `contracts/kernel-surface.json`：17 条接触面逐条声明 what / expect / probe /
  fallback / severity。覆盖外壳 12 条（运行时布局、runtime marker、启动行与 token、
  CLI+补丁启动、就绪码集合、/api 鉴权链、profile 清单 schema、bundle 声明、
  插件裸路由、补丁热重载语义、settings RPC、日志编码）与主题 5 条（设计令牌、
  模块加载器、DOM 锚点 12 个、slots API、渲染不变量 4 项）。
- `scripts/verify-kernel-contract.mjs` + `npm run verify:kernel`：Hermetic 验收
  （独立 `DSH_HOME` 临时目录 + 随机端口 + `--keep`/`--json`/`--timeout`），
  拉起真内核逐条探针，打印 PASS/WARN/FAIL/SKIP 报告，critical 失败退出码 1
  （即 CI 兼容门的判定依据）。**pending 行显式报「未接入」，绝不当通过。**
- 基线：`contracts/baselines/0.1.1-rc.1.json`（首跑结果存档，供将来 diff）。

#### 首跑基线（当前内核 0.1.1-rc.1）

13 通过 / 0 critical 失败 / 5 条未接入。要点：
- 启动行可解析（本世代无 token）、补丁内 file:// 插件行被加载、就绪码 200、
  `/api` 未启用鉴权、review-bridge 裸路由应答 409、空 home 内核自愈初始化清单。
- 主题静态探针：设计令牌 13 项命中、`__ModuleLoader__` 命中、**DOM 锚点 12 项
  在 101 个内核客户端产物文件里全部命中**——锚点分布确认在
  `@deepseek-ai/dsh-client-ui-*/lib/*.js`，所以改名可静态检出，不必等浏览器。
- `env.installed-plugins`：本机已装 5 个插件（super-injector / palis-theme-panel /
  auto-mode / better-sidebar / dsh-pet）全部可加载。

#### 实现中值得记的坑

- **stdout 必须按行装配**：套件自己就栽在这上面——直接对 chunk 跑正则时，
  `dsh-client-ui-*/lib/*.js` 这种注释里的 `*/` 会提前闭合块注释（JS 语法错），
  而真问题在语义上：启动行跨 chunk 分片会解析失败。外壳的 `captureWebUrl`
  正是这个写法（已知隐患，见〔103〕讨论），套件里做对了才能真实复现该探针。
- **内核自带 bundle 要从插件体检里排除**：`@deepseek-ai/dsh-base` / `dsh-web-app`
  由内核从运行时目录解析、不在 profile 的 node_modules 里，误检会全红。
  顺手把这份名单收成单一来源（`lib/profile-inspect.js` 导出 `CORE_BUNDLES`，
  main.js 与套件共用），避免三处各写一份而漂移。
- 空 home 的插件检查是空转的，所以另加 `env.installed-plugins` 只读检查真实
  profile——那才是内核升级时真正会坏的东西。

#### 维护约定（写在契约文件头部）

新增任何对内核的依赖（新锚点/令牌/API/启动行字段/文件布局）时同一条 PR 里补一行；
内核升级后跑 `npm run verify:kernel`，红项按 probe 名定位到本表再改代码。
5 条待接入探针（补丁热重载语义 / settings RPC / 日志编码 / slots API /
**渲染不变量**）——最后一条需要 CDP 实时渲染层（LayerTree 快照 + 逐帧圆度 +
DPR 2.73 仿真），是下一步的主要工作。

## 〔105〕 渲染不变量探针（契约 theme.render-invariants 接入）

#### 为什么单独一个脚本

其余契约探针是协议/文件级的（秒级、无浏览器）；这一条必须**真起浏览器 + 真渲染 +
逐帧采样**，才看得见「静态截图看不出来」的那类破坏——0.1.2 内核那次球体/月面/
声纳变形正是这一类（DOM 契约全中、截图逐像素是正圆，只有实时合成路径可见）。

`scripts/verify-render-invariants.mjs`（`npm run verify:render`，或
`verify:kernel --render` 由套件代为执行并汇总）。Hermetic：临时 `DSH_HOME` +
junction 挂入主题插件（与真实 profile 同构）+ 随机端口 + 临时 Chrome profile，
绝不碰用户实例。步骤：起内核 → `POST /api/palis-theme {theme:'palis'}` 打开主题 →
headless Chrome 以 **DPR 2.73 仿真**（复现本机环境）导航 → 等装饰层挂载 →
逐帧采样 40 帧 + LayerTree。

#### 四项不变量与实测（内核 0.1.1-rc.1，全绿）

| 探针 | 检查内容 | 结果 |
| --- | --- | --- |
| render.containing-block | 装饰层祖先链上不得有 transform/filter/backdrop-filter/perspective/will-change/contain（**根因检查**：这些一出现，absolute 层改按新包含块解析、fixed 层被捕获） | 7 个元素祖先链干净 |
| render.viewport-anchor | 每个 fixed 装饰层须横向通栏 + 垂直贴顶或贴底 | 全部严丝合缝 |
| render.circle-aspect | 圆形元素 40 帧内宽高恒等（=拉伸的直接判据） | 全部恒等 |
| render.dpr / render.compositing | DPR 仿真生效；合成层数与非常规 transform | 生效；LayerTree 无头下上报不稳，保持 warn 级不参与判定 |

#### 过程中的两个教训

- **探针的断言本身会错**：首跑 `.palis-statusbar` 报 FAIL——它是底部状态条（贴底、
  通栏），我却按"满屏层"要求它。判据改成「横向通栏 + 贴顶或贴底」才对。记录下来：
  这种验收套件的红项要先问"是产品坏了还是断言写错了"。
- **无头模式的 LayerTree 不可靠**（两次跑一次报 4 层、一次不报），所以合成层检查
  定为 warn 级、不进 critical 判定；真正的不变量判定靠几何采样（确定性强）。

#### 一条命令的全貌

`npm run verify:kernel --render` → 14 项通过 / 0 critical 失败 / 4 条待接入
（补丁热重载语义、settings RPC、日志编码、slots API）。基线存
`contracts/baselines/0.1.1-rc.1.json` 与 `contracts/baselines/render-0.1.1-rc.1.json`。

署名：ox-alpha
