# 2026-10-04

## 修复：scheme 模式下主界面永久「重新连接中」（0.1.45 埋下的 mux 断流）

用户报安装版（0.1.47）侧栏底部红色「重新连接中…」永不消失。顺藤摸瓜挖出一个影响**所有 scheme 模式构建**的断流 bug。

- **病灶链路**（全程实锤，无推测）：
  1. 页面（`dsh-app://app`）的全量数据走 remote.mux WebSocket：前端 `remoteStreamUrl()` 拿 `document.baseURI`（=`dsh-app://app/`）拼出 mux 地址，外壳注入的 WS 兜底（`makeWebSocketShim`）把它改写成 `ws://127.0.0.1:<port>/api/remote.mux` 让页面直连内核。
  2. Chromium 给 WS 握手带上 `Origin: dsh-app://app`（standard scheme 的必然行为；页面脚本受同源策略**无法**自改 Origin）。
  3. 内核 `isTrustedApiRequest` 栅栏：有 Origin 时要求其 host == Host 头——`app ≠ 127.0.0.1:<port>` → **恒 403**。且跨站 WS 连 Cookie 都发不出来（就算过栅栏也 401）。
  4. `ConnectionController` 指数退避重连 → 指示器永远「重新连接中」。
  - 聊天等核心功能之所以照常：它们走外壳 HTTP 转发（`forwardToKernel` 会剥 Origin、代持 cookie，天然合规）。**只有 WS 直连这条路漏了。**
- **取证**（零依赖 CDP 脚本，工作区根 `verify-mux-handshake.mjs`）：预览实例挂 `--remote-debugging-port`，抓 `Network.webSocketWillSendHandshakeRequest`——修复前 5 次握手全部 `403`（控制台风报 `Unexpected response code: 403`）、每 6–8s 重试一轮；仓库预览与用户安装版**同症**，排除"用户环境坏了"。
- **修法**（`main.js`，仅 scheme 模式挂）：`session.defaultSession.webRequest.onBeforeSendHeaders` 拦指向内核端口的 ws(s) 握手——剥 `Origin`/`Sec-Fetch-*`、代注 `state.webCookie`（内核栅栏对无 Origin 的回环 Host 放行，与 `forwardToKernel` 同一口径）。外壳本来就代持这份 cookie，此处只是把它补进页面直连的 WS 握手。
- **结果**：修复后预览实例 mux 一次握手 `101` 长连（挂监听刷新页面实测），「重新连接中」消失，会话列表/模型选择器/工作区全部加载。顺带治好同病灶的插件直连 WS（better-sidebar 终端/文件监听——shim 注释里说的"官方壳上本就是坏的"，现在这条路上 Origin 也被剥了）。
- **坑 / 备注**：
  1. 诊断中一度被 netstat 误导：页面对 13058「零连接」其实是采样时机问题——TIME_WAIT 堆积正是"连上→403→断开"的烟囱；后来 200ms 密采抓到 network 进程的两条 ESTABLISHED。
  2. Ctrl+Shift+I / F12 在安装版被禁（菜单「开发者工具」与 F12 都只在 DEV 下挂），页面侧取证只能走 `--remote-debugging-port`。
  3. 内核运行时仓库与安装版同为 0.1.7-rc.2（09-25），栅栏不是新引入的——是 shell 0.1.45 换 scheme 架构时与它撞上的。
- **改动文件**：`main.js`、`CHANGELOG.md`、`logs/2026-10-04.md`；工作区根新增 `verify-mux-handshake.mjs` / `verify-mux-101.mjs` / `verify-preview-state.mjs`（取证脚本）。
