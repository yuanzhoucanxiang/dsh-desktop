## 作品档案第五刀：wiki 变成真正的独立页面（独立窗口）

用户决定：「加跳转窗口吧，wiki 是单独的页面」。此前档案只有两种存在方式——写作台里的覆盖层、落盘的 .html。

- **做了什么**：
  1. **插件侧先有地址**（提交 755b587）：新增 `GET route=wiki`，返回 `text/html`。它与 `archive-export` 共用抽出来的 `assembleArchiveModel()`（同一份口径两个出口，不会再出现"面板里有、导出页里没有"这类漂移），但**不落盘**、每次现算、`cache-control: no-store`（缓存里的设定是过期的，比没有更糟）。响应带 CSP：`default-src 'none'; script-src 'none'; style-src 'unsafe-inline'` + `nosniff`——页内本来就没有脚本（导航全靠锚点），这条头是第二道防线。路径必须落在库根内且解析得出作品，否则 400；备忘坏 JSON / 未知 schema → 409，不猜不清空。
  2. **外壳侧开窗口**：新增 `shell:open-wiki` IPC（preload 暴露 `dshShell.openWiki(路径)`）+ `openWikiWindow()`。**刻意不做通用"开任意 URL"的口子**：调用方只给作品路径，URL 由外壳用 `kernelPageUrl()` 拼（协议/端口/token 都不出自外壳）；路径限长 500、拒控制字符与 `scheme://` 前缀；窗口数上限 6；同一作品复用同一窗口（重复点「档案」是聚焦，不叠第二扇）；走既有窗口配方（sandbox + contextIsolation + nodeIntegration:false + `hardenWindow`）；`restartKernel()` 与装更新清理里都 `closeWikiWindows()`（端口换了，旧地址已死，而它是投影、零丢失）。
  3. **客户端**：项目条「档案」优先走独立窗口，外壳没提供桥的环境（官方桌面、浏览器里跑插件）自动退回覆盖层并说明原因；覆盖层顶部也加了「独立窗口」按钮。
- **改动文件**：`main.js`、`preload.js`、`lib/shell-hardening.test.js`（S7 九条）、`plugin/writing-mode/index.js`（wiki 路由 + 组装函数抽取）、`lib/archive-html.js`（premiseOf 修）、`src/client/app/WritingModeApp.js`、`src/client/features/archive/index.js`、`client.js`、`CONTRACT.md`、`CHANGELOG.md`、工作区根新增 `verify-wiki-window.mjs`。
- **结果**：
  - `shell-hardening-test` **SHELL_HARDENING_OK**（含 S7 九条形状断言）。
  - 新增零依赖 CDP 取证脚本 `verify-wiki-window.mjs`：拿**真实文库**起一次应用（隔离 userData、共享 ~/.dsh），在应用页里真调 `dshShell.openWiki(E:\剧本\《在那寂静之后》)` → 新窗口出现、标题「《在那寂静之后》 · 作品档案」、目录与设定区在位、`document.scripts.length === 0`、`__pwned` 未定义、二次点击窗口数仍是 1 → **WIKI_WINDOW_OK**，截图 `verify-out/wiki-window.png`。
  - `test:writing-archive-html` 19 → **20 项**。全链 `verify:writing-quick` **603 项断言 0 非零**。
- **坑 / 备注**：
  1. **形状测试不等于能跑**。S7 断言的是代码写对了，但"顶层导航能不能穿过 dsh-app 代理拿到内核 cookie"只有起真应用才知道——所以补了 CDP 取证脚本，而不是写完形状断言就收。
  2. Node 26 里 `spawn('xxx.cmd')` 直接 **EINVAL**（不带 shell 不许起 .cmd）；要起 Electron 就指 `node_modules/electron/dist/electron.exe`。另外 Windows 下 `detached` + `process.kill(-pid)` 那套进程组杀法不成立，改 `taskkill /pid <pid> /T /F`，且只杀本脚本自己拉起来的那棵树。
  3. 真实作品立刻暴露一个显示毛病：页头「一句话」把空模板里的悬空标签「核心冲突：」当成前提渲染了出来。`premiseOf` 现在跳过"以冒号结尾 / 短于 6 字"的块，宁可不显示也不摆半截标签。
  4. 用户当前这部作品的档案是空的（0 条已确认设定、draft/ 下没正文）——这是**如实反映**，不是 bug：档案只收确认过的东西。空态文案已经写明去哪儿补。

## 作品档案第六刀：档案窗口里的作品切换条（顺带挖出 scheme 模式同源判定的老 bug）

用户说「按你的建议走下一步吧」——上一步的档案独立窗口一次只能看一部作品，库里有多部时就得回写作台再点一次。这一刀把「换一部看」放进窗口 itself。

- **做了什么**：
  1. **切换条是链接，不是控件**（`lib/archive-html.js` 的 `switcherSection`）：页头下方一排「换作品 ｜ 当前这部（粗体、不可点）· 另一部 · 另一部…」，条目是同源相对链接 `?route=wiki&path=…`，浏览器原生导航即可，页面 CSP 一字不改仍是 `script-src 'none'`。中间走过一条弯路：先做的是 `<select>` + GET 表单，形状都对、点了没反应——**Chromium 对 `dsh-app:` 这类非标准协议不提交 GET 表单**；退回链接后仍然点不动，才挖出下面第 3 条那个老 bug。
  2. **只列真渲染得出来的作品**（`plugin/writing-mode/index.js` 的 wiki 出口）：`scanTree` 在库根下有散稿时会把**库根自己**也冒成一条「独立文稿」，它没有 project.md 也没有大纲，列出来就是死链。滤它时撞到 Windows 陷阱：`resolveProjectDir` 返回 null 时若回落成空串交给 `fs.realpathSync`，**Windows 上 `realpathSync('')` 返回的是进程 cwd**——切换器于是列出一条指向 `E:\Deepseek harness\dsh-desktop`（仓库自己）的链接。现在两道闸：解析不出目录不列，解析出来但 `resolveUnderRoots` 说已不在库根内也不列。
  3. **修外壳老 bug：dsh-app 协议下自家地址全被判成跨域**。`isKernelPageUrl` 用 `new URL(x).origin` 比较，而 WHATWG 规定非标准协议的 origin 是字符串 `"null"`，`dsh-app://app/…` 的 origin 恰恰就是 `"null"` → 所有自家页面都不等于 `APP_ORIGIN`。后果不止切换条点不动：`will-navigate` 闸会拦下内核页里的普通链接，`sendToFocused` 的同源校验永不通过（scheme 模式下 Shell 事件静默不发），`restartKernel` 也走错分支。新增零依赖 `lib/url-origin.js`（origin 为 `"null"` 时退回 `protocol//host` 作键；解析失败/空值一律不同源，宁严不松），`main.js` 改走它。
- **改动文件**：`plugin/writing-mode/lib/archive-html.js`、`plugin/writing-mode/index.js`、`main.js`、新增 `lib/url-origin.js`（外壳根 lib，随 `build.files` 的 `lib/*.js` 打包，S8 已钉；插件的 `runtime-manifest.json` 只管 `plugin/writing-mode/` 下的文件，本轮无新增插件文件）、`lib/shell-hardening.test.js`（S8 八条）、`plugin/writing-mode/test/archive-html.mjs`（D01–D03）、`scripts/verify-writing-archive.cjs`（两段）、`CONTRACT.md`、`CHANGELOG.md`、`docs/audits/*` 复跑产物。
- **结果**：
  - `test:writing-archive-html` 20 → **23 项**；`verify:writing-archive` 13 → **15 段**（新增：服务端口径的链接形态/每条链接实测 200/伪作品不入列/库根 400 `no-project`；真导航的「在打开的档案页里点切换条，标题与正文换成另一部、上一部设定不残留」）；`shell-hardening-test` **SHELL_HARDENING_OK**（S7 九条形状 + S8 八条行为）；`verify:writing-quick` 全链 **26 个套件、566 段 PASS、0 非零退出**。真实文库 CDP 复跑 **WIKI_WINDOW_OK**（用户库里当前只有一部作品，切换条按设计不出现，脚本如实报"跳过切换验证"）。
- **坑 / 备注**：
  1. **形状断言抓不到"看起来对"的比较**。S7 那批断言查的是代码写没写对（有没有校验、有没有上限），而 `u.origin === APP_ORIGIN` 每一眼看都正确——只有真点一次才发现整片同源判定是失效的。所以 S8 是**行为**断言：先钉住平台事实（`new URL('dsh-app://app/api').origin === 'null'`），再钉 originKey 的产出。
  2. `file:` 在新键下会塌缩成同一个键（`file:` 的 origin 也是 `"null"`，退回去就是 `file://`），所以 `isKernelPageUrl` 绝不能放 file——本地页另走 `isAppFileUrl`，S8 专门钉了这条。
  3. 门禁 fixture 里加库根散稿这件事本身差点改写出问题：一开始把便签文件写在最上面的 fixture 段，写作台文档数从 8 变 9，前 10 段一起超时。伪作品只与切换条有关，就该只在那一段之前造——**fixture 的扰动要贴着被测面**。
  4. 切换条标签从「作品档案」改成「换作品」：页头副标题已经写着「作品档案 · 生成于 …」，同一屏两个"作品档案"读起来像标题重复。
