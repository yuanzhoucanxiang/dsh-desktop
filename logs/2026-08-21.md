### 6. A 案第一步：审阅 git 层落地（后端 + 单测，UI 待下一轮）

- **抽成纯 Node 模块** `lib/git-review.js`（`createGitReview(getCwd)`），三条理由写在文件头：
  ① 能用 `node lib/git-review.test.js` 秒级单测（真仓库真 git，不起 Electron）；
  ② **逐块补丁"现读现切"**——渲染侧只传 `{文件, 第几块}`，补丁在主进程重新从 `git diff` 切出来，
     避免拿旧补丁打到新文件上（脏了就 `git apply` 干净失败）；
  ③ 万一以后走生态原生路线（做成内核插件），这一层可整块搬走。
- **能力**：`stage` / `unstage` / `revertHunk` / `revertFile` / `commit` / `push`，
  以及给面板用的 `changes()`（新增 `diffUnstaged`、`diffStaged`、`hunksUnstaged`、`hunksStaged`、
  `branch`、`hasRemote`、`stagedCount`，同时**保留旧的 `diff` 字段**，老 UI 与老测试零回归）。
  实现细节：暂存块 = `git apply --cached`，取消暂存块 = `git apply --cached --reverse`，
  丢弃块 = `git apply --reverse`；整文件取消暂存优先 `reset HEAD`，无 HEAD（还没有提交）时退 `rm --cached`。
- **分寸（照 Codex 的手感）**：可逆的（暂存/取消暂存）**不打扰**；破坏性的（丢弃这一块）与对外发布的（推送）
  **必须二次确认**；提交前会先拒绝"空暂存区/空信息"。
- **单测 33 项全过**（`npm run git-review-test` → `GIT_REVIEW_OK`），最关键一条：
  `第 0 块仍在（LINE ONE 保留）` —— 证明逐块丢弃**只丢那一块**，不会把整文件还原掉。
  另外覆盖了：未跟踪文件、已删除文件、无远端 push 的人话报错、越界块序号、非仓库目录。
- `main.js` 只保留外壳职责（确认框 + IPC + 日志），`package.json` 的 `build.files` 已补 `lib/git-review.js`
  （否则打包版会漏掉这个模块 —— 这类"打包才炸"的坑必须当场堵）。
- 回归：`GIT_REVIEW_OK` + `sidebar-test` + `sidebar-layout-test` + `sidebar-skin-check` + `smoke` 全绿。
- **下一轮**：面板 UI（未暂存/已暂存分档、逐块按钮、提交框 + 推送）、以及"检测到 better-sidebar 就让位"。

### 9. 两处技术债处理（用户授权"都由你处理"）+ 发版 v0.1.11

**债务一：`dialog-optimize` 的内核私有 hash 类名。**
先核实再动手 —— 逐个看四处调用点，发现**它们本来就都有降级路径**：
`fullTextOf` 用整元素 textContent 兜底、`timeTextOf` 用 `/\d{1,2}:\d{2}/` 正则兜底、
「加载更早」提示与「撤回」按钮都是 `=== null` 就跳过。所以子代理"内核一升级就碎"的说法**偏重了**：
不会崩，真正的问题是**静默降级、查不出来**（撤回按钮不再出现，但没人知道为什么）。
于是按这个真实症状修：
- 4 个类名收进一处 `HASH_SEL`，全部调用点改走 `pick(scope, key)`
- 告警条件是「**从未命中过** 且已连续错过 30 次」，只报一次 ——
  不能"一没找到就报"，因为 `.Md3f7G_older button` 在没有分页历史时本来就不存在（会天天误报）
- 保留原有降级路径不变；`npm run selector-check` 继续在打包前做硬门禁
- 复核：`node --check` 通过，全文再无裸用 hash 类名（只剩 `HASH_SEL` 四行声明），`SELECTOR_CHECK_OK`

**债务二：本机 `dsh-better-sidebar` 里的路径炸弹。**
先判性质再删：`fsutil reparsepoint query` 报 `Error 4390: not a reparse point` ——
**不是软链/junction，而是真实物化的自嵌套副本**（顶层 `package.json` 与内层是同一个包
`@deepseek-ai/dsh-scope@0.1.0-rc.6`），深度 ≥400 层、最深路径 4082 字符、4096 文件 / 13.7 MB。
因为确认不是链接，才敢递归删（否则 `rmdir /s` 会穿透软链毁掉真包）。
`cmd rmdir /s /q "\\?\…"` 无效 → 改用**长路径删除的标准手法：robocopy 空目录 /MIR**，随后收尾。
结果：**4096 文件 / 13.7 MB → 7 文件 / 32 KB**，顶层包完好（`lib/` 2 文件 + package.json + 3 README + LICENSE）。
（这是仓库外的本机清理，不影响本项目产物；已在 CHANGELOG 如实记一条。）

**发版**：`package.json` 0.1.10 → **0.1.11**；CHANGELOG 把 `[Unreleased]` 收口成
`## [0.1.11] - 2026-08-21`（11 个顶级条目）并留空新的 `[Unreleased]`。

- 行 120 `MessageBox … "$(appRunning)"` ← 就是那句"应用没有完全关闭"
- 行 156 `MessageBox … "$(appCannotBeClosed)"` ← 杀不掉时的"请手动关闭"
- 行 115 `${if} ${isUpdated}` ← **只有带 `--updated`（应用内更新）才跳过提示**

**两条根因**（都修了）：
1. 用户多半是**手动双击安装包**（没有 `--updated`），而本应用「关闭窗口 = 最小化到托盘」，
   他以为退出了、进程其实还在；叠加安装目录内的 node.exe 文件锁 → 必然撞提示。
2. 应用内更新走的是 `autoUpdater.quitAndInstall()`，**默认参数 `isSilent=false, isForceRunAfter=false`**
   —— 等于主动让安装器带 UI 跑、装完还不重启。所以"点一下重启就好"在旧代码里根本不成立。

**修法**：
- **安装器侧**（`build/installer.nsh` + `package.json` 的 `nsis.include`）：用官方覆盖点
  `!macro customCheckAppRunning`（模板行 37 `!ifmacrodef customCheckAppRunning` 正是给这个用的）
  改成不问、直接收干净：`nsProcess::CloseProcess` 温和关 → `FindProcess`/`KillProcess` 强杀 →
  再用 `$PowerShellPath` 按 **ExecutablePath 是否位于 `$INSTDIR` 下**精确杀 node.exe
  （绝不碰用户机器上其它 node 进程）→ `nsProcess::Unload`。
  这条**手动双击安装包也生效**，所以 0.1.11 → 0.1.12 这一次就已经受益。
- **应用侧**：`quitAndInstall(true, true)`（静默 + 装完自动重启）；安装前先 `killChild()`、
  销毁托盘与附加窗口、留 600ms 让句柄释放；并开 `autoInstallOnAppQuit` 兜底。
- **可见性**：下载完成改发**系统通知**（点通知即安装），只有窗口可见时才额外弹选择框；
  选「稍后」后托盘顶部与「内核」菜单常驻「⬆ 重启并安装更新 vX」，不必重新下载。

**验证**：
- 构建日志**两次**出现 `warning: !warning: DSH: customCheckAppRunning override is active (…)
  (macro:customCheckAppRunning:4)` —— 分别对应 `installSection.nsh` 与 `uninstaller.nsh` 的插入点，
  **证明覆盖宏真的编进了安装器与卸载器**，不是"写了没生效"。这个 `!warning` 特意永久保留当证据。
- 顺带发现并修掉一个坑：include 是 UTF-8 无 BOM，makensis 按 ANSI 读 → 中文 `DetailPrint` 会变乱码；
  **所有给用户看的字符串改成 ASCII**（中文只留注释里）。
- 打包版冒烟：`SMOKE_HANDOFF acked=true` + `SMOKE_OK`，exit 0；`selector-check` 门禁在流水线里通过。

**没能验证的一步（如实说明）**：**我没有真的跑那个安装器**。因为 `customCheckAppRunning`
按可执行文件名杀进程，一跑就会杀掉用户此刻正在使用、并且正承载本次会话的那个应用实例。
真机验证留给用户：托盘 →「检查更新…」→ 下载完点通知或托盘里的「⬆ 重启并安装更新」。

### 11. v0.1.12 上线后翻车 → v0.1.13（连环三个自己挖的坑）

用户装 0.1.12 时报：`Failed to uninstall old application files. Please try running the installer again.: 2`

**取证**：`messages.yml:207` 是这句话的出处，`: 2` 是**老卸载器的退出码**（NSIS 用 2 表示被
`Abort`/`Quit` 中断）；`installSection.nsh` 显示 `CHECK_APP_RUNNING` 确实跑在 `uninstallOldVersion`
之前（时机没错），所以问题在**清理范围**。两处都是我写错的：

1. **只杀一次**。Electron 主进程 + GPU/渲染 helper 共 4~5 个同名进程，单次
   `nsProcess::KillProcess` 杀不干净 —— 而默认实现 `_CHECK_APP_RUNNING` 本来是**带重试循环**的，
   我把循环替掉了。老卸载器（0.1.11 自带、不含本修复）发现应用还在 → 静默模式 `/SD IDCANCEL`
   → `Quit` → 退出码 2。改为 `taskkill /F /T /IM` + 循环校验（最多 10 轮）。
2. **内核 node.exe 只按 `$INSTDIR` 过滤**，而 `uninstallOldVersion` 用的是注册表 `InstallLocation`
   （`installUtil.nsh:169`），两者可能不同 → 过滤可能整个空转。改为同时清 `$INSTDIR` +
   HKCU/HKLM `InstallLocation` 三个候选目录。

**修的过程中又连环踩三个坑（都记下来）**：

- **`!warning` 会让 NSIS 编译失败**：electron-builder 给 makensis 开了"warning 即 error"。
  我上一版用 `!warning` 当"覆盖已生效"的证据 —— 结果 NSIS 编译**直接失败**。改用 `!echo`。
- **`build.ps1` 会"假成功"**：PowerShell 不因原生命令非零退出而停止 → NSIS 失败后脚本照样打印
  `BUILD_DONE`，而 `dist/` 里留着**上一次的旧 exe**。于是我曾**基于陈旧产物**报告"构建成功"
  （0.1.12 发布的 exe 实际来自加 `!warning` 之前那次成功构建，内容是对的，但我的验证方法是错的）。
  已修：每步查 `$LASTEXITCODE`、构建前先删同版本旧产物、结束打印 `BUILD_OK version=… installer=…`。
- **PS 5.1 的编码地雷（踩了两次）**：
  · 用 `Get-Content -Raw | Set-Content` 给 package.json bump 版本，把中文 description 写成乱码带
    控制字符，npm 直接 `EJSONPARSE` → `git checkout --` 还原，改用 edit 工具。
  · 无 BOM 的 .ps1 被按 ANSI/GBK 读，中文注释会吞行尾 → `Unexpected token`；而 edit 工具保存时
    又会剥掉 BOM，形成死循环。**根治：`build.ps1` 改成纯 ASCII**（0 个非 ASCII 字节，注释全英文）；
    `release.ps1` / `prepare-runtime.ps1` 补 UTF-8 BOM。
  · 版本号一律 `node -p` 读，别用 `ConvertFrom-Json`（PS 5.1 解析不了带中文 description 的 package.json）。

**验证方式也按上次教训改了**：不再只看"文件存在"，而是**构建前删同名产物 + 看时间戳 + 看
`BUILD_OK` 明确输出**。0.1.13 实测：`BUILD_OK version=0.1.13`、`NPM_EXIT=0`、安装包时间戳
04:31（构建始于 04:29）、`latest.yml` = 0.1.13、打包版冒烟 `SMOKE_OK`、`GIT_REVIEW_OK`、
`SELECTOR_CHECK_OK`。另外「安装器里的清理是否真生效」现在由安装器自己写进详情日志
（`DSH: …` 若干行 + `kernel node.exe is free / still locked`），下次出问题可凭日志定位，不必再猜。

### 12. 用户仍装不上 → 一键安装脚本 + 修 `/T` 自杀（v0.1.14）

用户反馈"还是无法正常安装"，并猜「是不是安装过程中安装程序被当成了还在运行的软件」。
**这个猜测基本命中**，而且能指出确切机制：

- 应用内点「重启并安装更新」时，**安装器是应用的子进程**；
- 而我在 0.1.13 的清理里写的是 `taskkill /F /T /IM "<app>.exe"` ——
  **`/T` 连子进程一起杀，于是安装器把自己杀了**，安装当场中断。
- 修法：去掉 `/T`（只按映像名杀同名进程即可覆盖主进程与 helper），内核 node.exe 由第 4 步
  按可执行路径专门清理，不依赖 `/T`。

**同时给出不依赖安装器内部逻辑的一键脚本** `install-update.ps1` + `install-update.cmd`：
从安装器**外面**清理 → 静默安装 → 回读注册表验证 → 重新拉起应用。这条路径上不存在
"安装器把自己当成运行中的应用"的悖论。

**脚本的 dry-run 在用户机器上当场取证（比任何推理都硬）**：
```
name    : DeepSeek Harness Desktop 0.1.10      <- 我发的 0.1.11/0.1.12/0.1.13 一个都没装上
dir     : C:\Users\DL\AppData\Local\Programs\DeepSeek Harness Desktop
app processes    : 4                            <- 4 个同名进程活着
kernel node.exe  : 1  ...\resources\runtime\node.exe
file lock on runtime node.exe : LOCKED          <- 安装器要覆盖的正是这个被锁文件
```

**写脚本时被自己的 dry-run 抓到两个 bug（所以 dry-run 一定要先写）**：
1. `$MyInvocation.MyCommand.Path` 在**函数内部**指向函数而非脚本，返回 null →
   改用 `$PSScriptRoot`。
2. 注册表查错了位置。实测得到确切结构：
   `…\Uninstall\<GUID>` 里 `DisplayName = "DeepSeek Harness Desktop 0.1.10"`（**带版本号**，
   所以 `-eq` 永远匹配不上）、`DisplayVersion = 0.1.10`、**`InstallLocation` 是空的**；
   真正的安装目录在 `HKCU\Software\<GUID>\InstallLocation`（= NSIS 的 `INSTALL_REGISTRY_KEY`
   = `Software\${APP_GUID}`，见 multiUser.nsh:8）。
   → 顺带排除了一个诱人的错误假设："`InstallLocation` 为空导致 uninstallOldVersion 失败"——
     它读的是 `Software\<GUID>` 那个（有值），不是 Uninstall 键那个（空值）。差点写错结论。
   → 脚本改为：`-like "*名字*"` 匹配 + 目录优先取 `Software\<GUID>`、再回退 Uninstall 键的
     `InstallLocation`、最后回退卸载串所在目录。

验证：0.1.14 `BUILD_OK version=0.1.14`、打包版冒烟 `SMOKE_OK`、实际 taskkill 行已无 `/T`、
脚本 dry-run 能正确选中 `dist\dsh-desktop-0.1.14-setup.exe`。
仍未由我实测的是"真的点下去安装那一下"——脚本会关掉正在承载会话的应用实例，只能由用户执行。

## ⑰ 更新仍失败？根因是「长路径残留」：已修复并验证

- **现象**：应用内更新 0.1.15 → 0.1.16 点「重启并安装」后报
  `Failed to uninstall old application files. Please try running the installer again.: 2`
- **排查**（真机取证）：
  - electron-builder `--updated` 更新流程会**先把旧卸载器复制到临时目录**、用
    `/S _?=$INSTDIR` 跑它卸载旧版（`uninstallOldVersion` → 卸载器 `atomicRMDir` 把安装目录
    逐文件 `Rename` 到临时 `old-install`），任一文件搬不动 → `Abort` → 退出码 2 → 安装器 5 次
    重试后报错中止
  - 排除「应用没退出」：应用已关、无进程占安装目录（Restart Manager 确认）、卸载器从临时目录
    跑，**照样退出 2**；而不带 `--updated` 的普通卸载（走 `RMDir /r`）**退出 0**
  - **根因**：安装目录里 `resources\runtime\node_modules\@deepseek-ai\dsh-scope\dsh-scope\...`
    自我嵌套 **819 层、单条路径 8303 字符**（超 Windows MAX_PATH）。`Rename` 不处理长路径 →
    atomicRMDir 必然失败；`RMDir /r` 内部处理长路径所以没事。该残留来自旧构建（某版
    `dsh-scope` 包病态发布），NSIS 删不掉、跨历次重装累积
  - 关键对照：**repo 的 runtime 最深才 198 字符、外部 LOCALAPPDATA 运行时最深 217 字符，
    都是浅的** —— 深层残留只存在于安装目录
- **修复**：
  1. PowerShell（内部 `\\?\` 长路径支持）剪除安装目录里 **4803 个** >300 字符的深层残留
  2. 清掉半残安装目录 → 全新安装 0.1.16（安装目录最深路径 236 字符）
  3. **验证**：对浅的 0.1.16 跑 `--updated` 卸载模拟 → **退出码 0**（修复前必退出 2），
     随后重装并启动，内核从 `%LOCALAPPDATA%...\runtime\node.exe` 运行 —— **未来应用内更新闭环**
  4. **防御**：`prepare-runtime.ps1` / `prepare-runtime-macos.sh` 增加「剪除 >250 字符路径」
     步骤（提交 `ed7ccfb`），防止病态嵌套再进安装包
- **教训**：electron-builder 的 `--updated` 卸载（atomicRMDir/Rename）对长路径零容错；
  安装目录里一旦出现超长路径残留，更新必然失败且难以察觉。构建期剪除 + 需要时用长路径感知
  工具清理，是这类问题的正解
