## 〔100〕 mac 构建管线修复——v0.1.19 起 dmg 从未产出（用户「看看mac版本是否同步推送了」）

#### 结论先行：mac 从未同步成功

v0.1.30 release 只有 Windows 三件套（setup.exe / latest.yml / blockmap）。
查 Actions：`build-macos` 从 v0.1.19 起共 12 次运行**全部 failure**（11-16 分钟
后倒在 "Build dmg" 一步）；连更早的 v0.1.18 release 里也没有 dmg——
"tag 推送后 GitHub Actions 自动补 mac dmg"（release.ps1 注释）从未兑现过。

#### 三重根因（按失败日志反推）

1. **过时的内嵌拷贝 + 目标目录缺失（直接死因）**：build-macos.sh step 4 把
   `runtime/node_modules` 用 `cp -R` 拷进 `.app/Contents/Resources/runtime/`——
   这是 v0.1.17 之前的旧架构（当前架构 = 归档 + 首启动解压）。且 `cp` 的目标父
   目录 `Resources/runtime` 在 .app 里根本不存在 → 逐文件 `No such file or
   directory` → exit 1。这条拷贝本身就该删除。
2. **从未打包 runtime.tar.gz + runtime-marker.json**：构建日志里
   `file source doesn't exist from=dist/runtime.tar.gz`——extraResources 引用的
   归档在 mac 侧从未生成（Windows 由 build.ps1 打，mac 的 build-macos.sh 没有
   对应步骤）。即使 cp 修好，.app 里也没有内核，首次启动 `ensureExternalRuntime`
   直接跳过归档、`resolveDynBin` 兜底也找不到运行时 → 无内核可用。
3. **prepare-runtime-macos.sh 不写 runtime.json**：Windows 侧
   prepare-runtime.ps1 写 `{dsh,node,builtAt}`，mac 侧漏了——`runtime-marker.json`
   无源，`ensureExternalRuntime` 无法比对版本。

**附加坑**：step 3 写成 `npx electron-builder --mac dmg --dir`——dmg 目标+`--dir`
混用，electron-builder 直接出了个**不含运行时**的残缺 `dsh-desktop-0.1.30-mac.dmg`
+ blockmap（日志 08:13:03 "building target=DMG"），很容易误判"其实构建过"。

#### 修复（提交 dd60d8b / a8779c5）

- **prepare-runtime-macos.sh**：runtime 就绪后写 `runtime/runtime.json`
  （`{dsh,node,builtAt}`，字段与 prepare-runtime.ps1 同构；dsh 版本经 argv 传入，
  注意该变量未 export，不能走 process.env）。
- **build-macos.sh**（对齐 build.ps1 两步法）：
  · runtime 就绪后立即 `tar -czf dist/runtime.tar.gz -C . runtime` + 复制方法
    `runtime-marker.json`（归档内容带 `runtime/` 前缀，与 Windows 同）；
  · step 3 改 `--dir`（不再传 dmg 目标，禁止中途产出残缺安装包）；
  · 删除过时的内嵌 node_modules 拷贝块；
  · step 5b 生成 `latest-mac.yml`——`--publish never` 不产清单，mac 检查更新会
    404（与 2026-08-25 Windows latest.yml 同坑不同面）。
- **gen-update-manifest.js**：新增第 4 参数输出文件名（缺省 latest.yml），
  mac 传 latest-mac.yml；本地实测（dummy dmg）输出格式正确。

#### v0.1.30 新代码 mac 兼容性核查（无问题）

hardenWindow(fileURLToPath/path.relative 均跨平台)、mdInline（纯 DOM）、
git-review(path.isAbsolute)、preload（contextBridge）——无 mac 特有 API；
打包态 `app.getAppPath()` = `.../Contents/Resources/app.asar`，isAppFileUrl 的
path.relative 判据对它成立。

#### 重构验证

- 本地：`bash -n` 两个脚本通过；node 侧 runtime.json 写入器与清单生成器实测通过。
- CI：`gh workflow run build-macos.yml -r main`（workflow_dispatch）在 main
  最新提交（a8779c5）上重跑——**成功**（run 34126717100，Build dmg 16m47s，
  Publish ✓）。
- 资产：`dsh-desktop-0.1.30-mac.dmg`（185.69 MB / 194720239 B）+ `latest-mac.yml`
  已上传 v0.1.30 release；构建日志确认 `runtime.tar.gz (81M)` 打包、清单生成
  （sha512/size 与 dmg 一致）、BUILD_DONE。mac 版本自此补齐——Windows 三件套
  + mac dmg + 双 latest 清单，两个平台更新闭环齐了。
- 坑记录：①`DSH_VERSION` 未 export，node -e 子进程读 process.env 拿不到——
  改走 argv 传参；②`gh run view --log-failed` 的 cp 报错噪点大，但
  `file source doesn't exist` 那行才是根因指纹；③先前推 dd60d8b 时 SSH 断连，
  `tail -1` 显示的是 "and the repository exists."（报错尾巴）被误判为成功——
  推送后必须 `ls-remote` 复核远端 HEAD（本次靠 HTTPS 补推）。

## 〔101〕 内置插件机制（v0.1.31，用户「有一些插件也放进去吧」）

#### 需求与方案

mac 版开箱即用 4 个插件（用户确认全选）：dsh-better-sidebar 0.15.2 /
@nanmicoder/dsh-auto-mode 0.1.2 / dsh-pet 0.1.4（npm registry）+ @dsh-local/
palis-theme-panel 0.4.3（自研，构建产物随其仓库 tag 的 Release 资产分发——
lib/ 不入 git，CI 无法现打，于是补了 v0.4.3 tarball 资产）。

链路：构建期 scripts/prepare-builtin-plugins.mjs 装出 stage 树（默认
dist/builtin-plugins，可 DSH_BUILTIN_OUT 指工作区外）→ extraResources
`dist/builtin-plugins → builtin-plugins` → 首启 main.js seedBuiltinsIfNeeded()
（内核 loadProfile 自愈式初始化 profile 后，补种 + 重启内核一次）→
lib/builtin-seed.js（纯模块，16 项单测）。

#### 踩坑记录（重要）

1. **npm 装插件树失败**：三者同装 eresolve（peer 版本族打架）；npm 11 还会把
   peer 藏进嵌套 node_modules（@deepseek-ai/* 顶层缺失）。改用 **pnpm +
   node-linker=hoisted**（与 `dsh plugin add` 同构；pnpm 11 的
   `--config.node-linker=hoisted` 走 CLI 传，.npmrc 实测不被读取）；
   win 平台删掉 --no-frozen-lockfile（pnpm 11 已移除）。
2. **peer 版本漂移（最险）**：插件 peer 只写范围（如 ^0.1.0-rc.8），pnpm 自动
   解析选到 registry 当前最高满足者（实测 dsh-settings 解析到 **0.1.0 稳定版**，
   auto-mode 系要到 0.1.2-rc.1 族）——而运行时是 0.1.1-rc.1 族，同 service
   双版本同进程必乱。修法：pass1 装插件 → 读各插件 peerDependencies 中
   @deepseek-ai/* 名 → 按**运行时实际版本**精确写进 stage package.json →
   pass2 重装（pnpm 解析必取其值）。用户 profile 当年解析出 rc.1 只是时点巧合。
3. **electron-builder 的 extraResources 默认跳过名为 node_modules 的子目录**
   （实测 builtin-plugins 只进了 manifest.json——老 mac 脚本注释里其实写过这句
   教训）。修法：stage 树目录名改 `packages/`（种子按同名读取）。
4. **体积：410MB → 62MB**。npm/pnpm 把 client-only 依赖（react-icons 85M /
   mermaid 83M / node-pty 64M / @codemirror 全家）全装成一棵平铺树。依据：
   ① client 产物 lib/client.js 是 rolldown 单文件 bundle（29 处命中均为内联
   实现）；② 服务端 import 闭包只有 schemastery + ws + @deepseek-ai/*。裁剪后
   只留 7 个顶层结点。注意：若插件升级新增服务端裸依赖，白名单要同步加。
5. **触发时序毛刺**：种子最初挂在 waitReady（内核就绪瞬间）→ 与 splash 交接/
   loadURL 并发，实测一次 ERR_ABORTED + 内核二次启动（最终收敛）。改为
   bootKernel 收尾触发（交接完成后），提交 30dfd45，tag v0.1.31 强制移指。
6. **版本选型**：npm latest（auto-mode 0.1.7 / pet 0.2.6 / sidebar 0.18.0）peer
   都指向 0.1.2-rc.1 族 → 与运行时 0.1.1-rc.1 族不兼容；改为 0.15.2/0.1.2/0.1.4
   （peer ^0.1.0-rc.6/rc.8 族，运行时满足）。
7. 其它：ZCode 监视器锁工作区内新建大树（stage 输出指 %TEMP%）；pnpm 从
   registry 下载超时（DSH_BUILTIN_REGISTRY 支持换 npmmirror）；Node 20.12+
   spawn .cmd 需 shell:true（改 node 直跑 npm-cli.js / pnpm.cjs）。

#### 验证

- 单测全绿：builtin-seed（16）+ git-review + profile-inspect（7）+
  plugin-manager（19）+ atomic-file（14）。
- Windows v0.1.31 装机实机：setup 234MB（含 52M 内置插件增量）；
  kernel.log 出现 `builtin plugins seeded: <4 插件>` + 重启 + stamp 落盘
  （userData/builtin-plugins-seeded.json）；新内核 1577 起来，4 进程运行。
- mac workflow（tag push 触发，run 34134443154，修复后代码）：**成功**；
  `dsh-desktop-0.1.31-mac.dmg`（226MB，含内置插件）+ latest-mac.yml 上传
  v0.1.31 release；构建日志确认 prepare builtin（10s）/pruned 184→7 结点/
  BUILD_DONE。v0.1.31 五件套齐：win setup / win blockmap / latest.yml /
  mac dmg / latest-mac.yml。
