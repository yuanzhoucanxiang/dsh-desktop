## 写作模式 P1-③（R7 漏报盲区：定位并修好）

上一条遗留第 3 项。这次把它查到根因，并给 R7 配了**自身敏感性自检**。

### 根因

给 R7 加了 `--debug <名字>`（逐条规则复算"是谁把它当成声明"）后复现定位：
摘掉 `WritingCompanion` 的 import 后，R7 仍判它"已声明"，而且指出是**参数位置**规则。

```js
...text.matchAll(/\(([^)]*)\)\s*=>/g)   // ← 病灶
```

`[^)]*` **可以跨行**：某段跨 3 行的箭头参数括号里正好包着 `jsx.jsx(WritingCompanion, {…})` 的用法，
于是整个用法被当成"箭头形参"，`WritingCompanion` 进了本模块的声明集合 → 静默放行。
（同一类病灶还有 `/\{([^}]*)\}/`、`/\[([^\]]*)\]/` 的解构提取，都会跨行吞代码。）

### 修法

新增 `balanced(text, openIndex)`：**严格括号配对**（栈式，遇不匹配的闭括号即保守结束），
形参/箭头参数/catch 参数/解构全部改为"配对后取内部标识符"，`[^)]*` 一类跨行正则全部移除。

### 证据（自检脚本 `scripts/verify-writing-imports.selftest.mjs`）

把 `src/client` 复制到临时目录 → 注入漏 import → 期望 R7 失败并点名；另有阴性对照与复原校验：

| 场景 | 结果 |
| --- | --- |
| 阴性对照（未注入） | PASS（无误报） |
| 主应用漏 import 组件（历史漏报现场） | **FAIL 并点名 WritingCompanion**（修好前是静默 PASS） |
| 记忆 feature 漏 import 服务模块 | FAIL 并点名 api |
| companion 从多名 import 里漏一个（最隐蔽形态） | FAIL 并点名 getDraftStatus |
| 复原后 | PASS |

自检已并入 `npm run verify:writing-architecture`（R1–R6 + R7 + R7 自检）。真机 `verify:writing-imports` 仍 PASS。

**教训**：只会说 PASS 的检查器不可信 —— 凡是"检查器"，都要有一条"注入缺陷后它必须报错"的证据。

### 交付语义（逐条对应方案）

- **受理三分**：`send()` 返回 `accepted | rejected | uncertain`；uncertain 先核对原生回合/队列证据

- **迟到归位**：handle 绑定自己的 projectKey/sessionId/token，异步返回后先核身份再交付；A 的草稿不会发进 B。
- **不静默新建**：会话被删 → `missing` + 恢复入口；创建结果不可确认 → `uncertain` 并保留已知标识；
  只有作者点"继续关联"才 `forget` 后重建。
- **dispose 只释放订阅**：不取消模型任务、不删会话、不动协调记录（fixture 断言）。
- **UI 不碰 native**：`companionRows` 改为消费 adapter 投影的 `messages`，`chat.nodes/order` 只出现在 projection.js。
