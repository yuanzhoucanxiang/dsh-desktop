## 写作模式 v2 二次整改返工（N01–N06）+ v0.1.39 发布

### 复核（二）六项的修法

- **N01（最严重）**：打包门禁收尾用 `taskkill /IM "DeepSeek Harness Desktop.exe" /F` 按镜像名批量结束进程，
  会连用户正在用的正式桌面一起结束。改为 `lib/pid-cleanup.js` 只按**本轮 spawn 的 PID** 清自己的进程树；
  新增 `lib/pid-cleanup.test.js`：两个同名同命令行假进程，只登记一个，断言另一个仍存活。
- **N02**：`recover()` 先查内核保存的项目关联与已知 workspace 对应的原生会话，查不到就保持 uncertain，
  不再把"未知外部结果"当成"没有会话"去重建。
- **N03**：采用候选绑定项目 + 编辑代数；迟到返回若发现新编辑则取消采用并保留新稿；采用改为一次 store 操作。
- **N04**：明确拒绝不再被文本包含关系翻案；抛异常只在有内核可证明标识时才算受理，否则 uncertain。
- **N05**：`checkTrustedBoundary()` 三层校验（根/祖先/子目录）+ 调用方 `trustedRoot`；
  修掉"可信根必须存在"导致首启同步被拒的自伤。
- **N06**：严格门禁（缺真包非零退出）与开发态快速门禁分离；记录被测源码 SHA/dirty 与 app.asar sha256；
  asar 主进程模块逐字节比对 + 全模块仓库路径检查；升级 fixture 接到生产路径并用生产模块验证
  可发现/可读/可继续保存；矩阵 30 项按子场景归类（6 PARTIAL）。
- **C02 面板**：待定问题勾选才带入；"优先"只对可自动带入条目；预算省略数改用 `omissions` 计算。

### 构建为什么没走 `release.ps1`（等价步骤 + 已验证载荷）

`release.ps1` → `build.ps1` 在本机**无法就地构建**：`electron-builder --dir` 要写
`dist/win-unpacked/resources/app.asar`，而该文件被 ZCode 会话进程锁住（`EBUSY: resource busy or locked`），
这是仓库日志里记录过的已知坑（普通终端不受影响）。因此改为**等价路径**：

1. 首次失败还暴露了另一个环境问题：`electron-builder` packaging 阶段去 GitHub 下载 electron 超时
   （`connect ETIMEDOUT 20.205.243.166:443`）。已用"指向本地 `node_modules/electron/dist`"绕过
   （**仅本次构建的临时配置，发布后已还原**——tag 上的 package.json 不含这些改动）。
2. 在 `%TEMP%/wm-v2-release-0.1.39` 构建 dir 包（版本 0.1.39）→ 写 `resources/app-update.yml`（与 build.ps1 同内容）
   → `electron-builder --win nsis --prepackaged <dir>` 出安装包 → `gen-update-manifest.js` 出 `latest.yml`。
   **用 node 直跑 electron-builder 的 CLI**：`.bin/*.cmd` 是 shell shim，工作区路径含空格时会被 cmd 拆开（已踩多次）。
3. 发布前验收**安装包里的同一份载荷**：`verify-writing-package --package` 7/7（asar 主进程模块**逐字节一致**、
   插件 15 文件一致、资源完整）、`verify-writing-packaged` **9/9**（真包冷启动、首启种子、主题开启/恢复、
   按本轮 PID 清理）。
4. 资产上传后逐项核对：远端 digest == 本机 sha256。
