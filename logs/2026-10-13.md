| ④ 拖动主窗 → 圆点跟随吗 | **✗ 未解决（且我的测法有局限）** | 主窗 +300,+120（外部 `SetWindowPos`）后浮标原地不动 |

### ④ 的根因（比"忘了写处理器"更深）

- `main.js` 里 `win.on('move'/'resize', syncWorkbenchOverlay)` **本来就有**（Qoder 写的），不是漏挂。
- 实测：外部移动主窗后，应用自报 `getWorkbenchShape().bounds` 仍是**旧位置**（报 971,16，OS 实际已到 2251,204）
  → `overlayBounds()` 用旧几何算出旧位置 → 浮标不动。即 **`win.getBounds()` 读不到"外部发起的移动"**。
- **诚实边界**：这只证明了"外部程序移动"这条路径；**真实用户拖动没测成**（拖动脚本那一次窗口枚举失败、
  坐标算成 (0,18)，见下面"操作事故"）。所以 ④ 现在只能记 **未证实**，不能写成产品缺陷。

### 修了什么（防御性；真机 A/B 有证据，反例实证**没做成**也如实记）

1. `applyWorkbenchShape()` 末尾补 `syncWorkbenchOverlaySoon(0)` + `(160)`——形态落定后重摆浮标。
2. `showWorkbenchOverlay()` 创建后补摆 `[0,120,400]ms`——治"浮标先于形态创建"的竞态。
3. `move`/`resize`/`restore` 处理器改走去抖版 `syncWorkbenchOverlaySoon()`（拖尾补一次，拖动时不抖）。
- **真机 A/B**：修前 `open` 后浮标页 `screenX=0`（贴屏幕最左、离长条 1000+ px）；修后 `screenX=663` ✓ 贴住长条。
- **反例实证失败（记下来）**：把上面两处补摆分别关、再一起关，探针新增的 G2/G3 仍然绿——
  探针里 `resize` 处理器总会兜住，**复现不了真机那条竞态**。所以 G2/G3 是"不变量"而不是"回归锁"，
  竞态的证据只有上面那次真机 A/B。要真正锁住它，得让探针能制造"setBounds 之后立刻开浮标"的时序，
  或者干脆把浮标位置改成由主进程在每次 `setBounds` 后主动算（不依赖事件）。

## 浮标整体移除 + 长条"裸奔"修复 + 置顶阶梯互斗的根因（deepseek-v4.1-flash）

用户两条指令：①"这个浮标没有用就去掉"；②"竖直长条里面的前端内容不对"。

### ② 的根因：不是"内容画错"，是**主屏根本没开而形态留在条状**

- 实测：长条里 `.dshWbHome` 是 `fixed` + 不透明（`rgb(21,21,23)`）+ `z-index:2200` **铺满**的——
  所以内容不对不是它没画，而是**它没开**：页面重载 / 插件重挂之后 `open=false`、`askedForStrip` 归零，
  而壳还停在条状 → 长条里只剩内核自己的界面（侧栏 + hero + 会话），浮标卡片再叠上去就是你看到的样子。
- 修：门面**挂载时对账一次**——读 `getWorkbenchShape()`，非 `normal` 且主屏没开就还回 `normal`
  （不常驻轮询，只挂载时一次）。
- 实测：重载前 `strip` + 主屏不在 → 重载后 `shape=normal`、窗口回 **1363×763** ✓

### ① 浮标整体移除（壳 / preload / 门面 / 门禁四处）

- 壳：`showWorkbenchOverlay` / `hideWorkbenchOverlay` / `syncWorkbenchOverlay(Soon)` / `overlayBounds` /
  `overlayHtml` / `OVERLAY_W·H` / `overlayWin`、两条 IPC（`shell:open-workbench-overlay`、
  `shell:close-workbench-overlay`）、`shapeState().overlay`、主窗 `move/resize/hide/minimize/restore`
  上的浮标钩子、`closed` 里的兜底——全删。
- preload：`openWorkbenchOverlay` / `closeWorkbenchOverlay` 两个方法删。
- 门面：`requestOverlay` 删、`Chrome.js` 三处调用删。**漏了一处**（`toggleMini` 里的），
  被 `verify:workbench-ui` 当场抓成 `requestOverlay is not defined` 的 RENDER ERROR——探针的价值就在这。
- 门禁：`verify:shell-shape` 的 G/G2/G3 三条浮标断言 → 换成**反向守卫**（`dshShell` 上没有任何
  `*Overlay*` 方法 + OS 里没有残留浮标窗）；`verify:workbench-ui` 的假桥不再提供这两个方法 +
  断言"一次都没调过"。理由：**防将来有人把它加回来却不知道当初为什么删**。

### 顺手挖出并修掉一个真缺陷：置顶补刀阶梯**互相打架**

- 现象：`verify:shell-shape` 的 H 段开始**间歇性红**（`topmost:false`，应用自报也是 false，**日志却是空的**）。
- 根因：连续切形态时（门禁的 B→C→E→F→H 就是连着切），**上一次"取消置顶"的阶梯会在后一次"置顶"之后落地**，
  把刚置上的位清掉；阶梯越长、重叠窗口越大——我先前把它从 1500ms 延到 2500ms，正好放大了它。
  日志为空也解释得通：第一次调用时 `isAlwaysOnTop()` 返回 true（阶梯收手），位是**之后**才被旧阶梯清掉的。
- 修：`topmostJobs`（WeakMap）**同一窗口只保留最新一次意图的阶梯**（新申请取消旧 token + 清定时器）；
  另加**有界落地复核**（1.5/3/5/8 秒各查一次，落上就停、换形态即取消），覆盖"调用当场成功、几秒后位丢了"。
- 实证：修前 3 轮里红 1 次；修后**连跑 4 轮全绿**（长条 ~360ms 稳定落位，`ex=200108`）。
