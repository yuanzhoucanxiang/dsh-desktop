## 浮标整体移除 + 长条"裸奔"修复 + 置顶阶梯互斗的根因（deepseek-v4.1-flash）

### ② 的根因：不是"内容画错"，是**主屏根本没开而形态留在条状**

- 实测：长条里 `.dshWbHome` 是 `fixed` + 不透明（`rgb(21,21,23)`）+ `z-index:2200` **铺满**的——

  （不常驻轮询，只挂载时一次）。

### 顺手挖出并修掉一个真缺陷：置顶补刀阶梯**互相打架**

- 现象：`verify:shell-shape` 的 H 段开始**间歇性红**（`topmost:false`，应用自报也是 false，**日志却是空的**）。
- 根因：连续切形态时（门禁的 B→C→E→F→H 就是连着切），**上一次"取消置顶"的阶梯会在后一次"置顶"之后落地**，
  把刚置上的位清掉；阶梯越长、重叠窗口越大——我先前把它从 1500ms 延到 2500ms，正好放大了它。
  日志为空也解释得通：第一次调用时 `isAlwaysOnTop()` 返回 true（阶梯收手），位是**之后**才被旧阶梯清掉的。
- 修：`topmostJobs`（WeakMap）**同一窗口只保留最新一次意图的阶梯**（新申请取消旧 token + 清定时器）；
  另加**有界落地复核**（1.5/3/5/8 秒各查一次，落上就停、换形态即取消），覆盖"调用当场成功、几秒后位丢了"。
- 实证：修前 3 轮里红 1 次；修后**连跑 4 轮全绿**（长条 ~360ms 稳定落位，`ex=200108`）。

### 契约（门面侧）：`splice`

模式可以交 `splice: { label, mount, view, width }`：
- **`mount(container)`** —— 给**单实例模式**（写作台就是）：它把**同一个界面实例**渲染进我们给的容器，
  返回 dispose；收起拼接时调它。为什么不挂第二份、也不搬 DOM：单实例的编辑会话 + 按窗口 id 分桶的
  草稿恢复会互相覆盖（坞视图头注早有此教训）；React 17+ 的事件委托挂在根容器上，挪出那棵树事件就哑了。
- **`view`** —— 可自由重挂的模式直接给组件引用。
- **`width`** —— 模式自己声明期望宽度（写作台 720；三栏界面在 420 里会被裁，实机截图确认过）。
- 都没有 → 退回 `dock` 轻视图（旧降级路径，如实呈现）。

门面新增 `Splice.js`：渲染容器 `.dshWbSpliceHost{position:relative}`、按 `mount`/`view` 分流、
卸载时 dispose、挂 `data-wb-splice-source` 标明走的哪条路。探针 **⑫ 组**：mount 调一次 / 模式挂进来的
内容真在列里 / 来源 `mount` / 没同时退化成坞视图 / **声明 600 就申请 600** / 收起时 dispose 恰一次且内容清掉。

## 修"扇形刚呼出、鼠标还没挪过去就消失了"（deepseek-v4.1-flash）

项目所有者附截图（扇形里"写"在上、"G"在下）实报：「这个图标呼出时，鼠标还没挪过去就消失了」。

### 根因是**几何**，不是状态管理

- 命中区 `.dshWbSeam`：**贴右缘 26px 宽的整高条**；
- 图标项：`rotate(a) translateX(-58px)` —— **往里弹 58px**，落在条**外面**；
- 于是鼠标从条上往图标走的**半路上就出了命中区** ⇒ `mouseleave` ⇒ `setSeamOpen(false)` ⇒ 扇形没了。

### 两处一起兜（只做一处都不够）

1. **展开时把命中区撑到覆盖扇形**：`.dshWbSeam.is-open{width:132px}`（26 边条 + 58 弹出 + 46 图标 + 余量）。
   只有展开时才变大，平时仍是 26px，不挡长条内容。
2. **离开给宽限**：`SEAM_CLOSE_GRACE_MS = 240`；`openSeam()` 取消待收定时器、`scheduleCloseSeam()` 起一个；
   进到图标上（React 的 enter/leave 合成会把 mouseover 传到接缝上）或重新回到条上都会取消；卸载时清定时器。

为什么"撑命中区"不够：鼠标也可能**先离开条、再斜着插进图标**（走一条不经过撑开区域的路径）；
为什么"只加宽限"也不够：240ms 对慢速移动的人不够，而且离开后扇形还亮着会让人以为点得上。

### 探针（⑩ 组补四条，都是按**时序**判的）

展开时命中区 **>100px**（关着是 26）· `mouseout` 后 **60ms 仍开着**（宽限生效）·
`mouseover` 到某一颗上 **400ms 仍开着**（取消关闭）· 彻底离开（超过宽限）**才收**。

`WORKBENCH_BRIDGE_OK 12` · 构建 **117,055 B** 逐字节一致 · 全链退出码 0。

## 模块化第一刀（壳侧模块窗口）+ 测试实例放非主屏（deepseek-v4.1-flash）

## 测试实例仍跑到主屏：两处漏网（deepseek-v4.1-flash）

项目所有者再报「还是有测试实例会跑到我主屏上」。查出来是**两处**，都不是"变量没设"这么简单：

1. **"保存的位置"会盖过目标屏**：探针/链路会先往隔离 userData 写 `settings.json`（带上一次的主屏坐标），
   而首窗逻辑是"有记忆就按记忆" ⇒ 目标屏被绕过 ✗。修：**指定了目标屏时，目标屏优先于保存的位置**
   （尺寸仍取记忆值、再夹进目标屏；没指定时行为不变）。
2. **只给个别命令带了变量**：全链里别的脚本 spawn 的实例照样弹到主屏 ✗。修：**隔离实例默认去非主屏**——
   `displayEnvRaw()`：显式 `DSH_DESKTOP_DISPLAY` 优先；没写但**带了 `DSH_DESKTOP_USER_DATA`**
   （探针/预览/链路都是这种隔离实例）就默认 `secondary`；**真实桌面版不带这个变量，行为一点不变**。

实测：只带 `DSH_DESKTOP_USER_DATA` 起一个实例 → 窗口落在 `{x:8, y:800, w:1081, h:686}`
（非主屏工作区之内）✓。这条写进 AGENTS §2.2，下一位协作者不用再靠"记得设变量"。

用户澄清："**左边是写作模式的 agent 对话窗口——我说的是「写作助手」**"。所以左侧不是"以后再说"的位置，
而是**该模式自带的助手对话**；一个模式可以同时有**两块**模块窗口。

### 改动（外壳 `937846c` + 插件提交 + 指针）

- **契约**：`splice.assistant`（`true` 或 `{ width }`）——模式声明"我还要一块助手窗口"。
  registry 归一化（默认 360、下限 260）并由 `spliceViewOf` 透出；门面在主窗口开成功后**再开一块**，
  带 `kind='assistant'`（`shell-shape.js` 透传 kind）。
- **壳**：模块窗口的键带上 kind（`id` = 主界面、`id/assistant` = 助手），两块可并存；
  closeModuleWindow 带 kind 只关一块、不带则两块一起关。
- **写作模式**：`setWritingSplice({ …, assistant: { width: 360 } })`；助手窗口里按 URL 片段认领自己并
  打开写作伙伴面板（复用上一刀的 `WritingModeApp` moduleWindow 逻辑）。
- **探针 ⑪**：声明 assistant 的模式应**一次开出两块**（main 用 `splice.width` 640、assistant 用 300），
  壳记账里两种 kind 都在；关掉时不带 kind ⇒ 两块一起关。

### 顺手修掉的真缺陷：助手**压在长条上**

第一次实机量到 `[助手 0..222][长条 182..603][主界面 603..1078]` —— 助手**重叠长条 40px** ✗。
原因：长条左边只剩 182px，而模块窗口 `minWidth: 220` 让 `setBounds` 缩不下去，位置兜底又只能取 `area.x`。
修：**左侧助手窗独立下限 160**（`MODULE_ASSISTANT_MIN_WIDTH`）+ 模块窗 `minWidth` 220 → 160。
再量：`[助手 59..420][长条 419..841][主界面 841..1079]` —— **不重叠、不出屏、紧贴** ✓。

### 我犯的两个错（都记下来，别重复）

1. **提交了一个会报错的 preload**：`ensureModuleWindowTrim()` **只有调用、没有定义**——
   那条编辑因为 `old_string` 匹配到两处而失败，我没回头确认就提交了。教训：**编辑报错必须回头核**，
   尤其"我加了调用"和"我加了定义"是两条独立编辑时。
2. **注入挂在 `applySkin()` 里 ⇒ 主窗里拖拽带一个都没注入**：那条路径要等 `shell:get-state` 回来，
   而页面早就 `DOMContentLoaded` 过了。**这才是"整体拖动不了"的真因**（我先前以为是顶栏没设拖拽区）。
   修：`bootstrapShellInjections()` 在 **preload 顶层直接调用** + `DOMContentLoaded`/`load` 双兜底（幂等）。
   教训：**preload 里的注入不要依赖"等某个异步结果"再挂事件**——那时事件已经过去了。
