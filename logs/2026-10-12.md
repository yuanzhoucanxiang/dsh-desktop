## 修复：首屏被「界面已关闭」遮罩糊住（hidden 属性失效）

- **现象**（用户报告 2026-10-12 04:45）：strip.html 打开就是一片模糊遮罩 + 「界面已关闭（原型示意）」——首屏什么都看不到。
- **根因**：`.closed`、`.mini` 等类里写了 `display:flex`，作者样式里的显式 display 会**盖过** `hidden` 属性的 UA 样式（`[hidden]{display:none}`），于是初始就带 `hidden` 的关闭遮罩（#closedVeil）和小长条（#mini）一加载即显示。同错误在 index.html 也有：#modeOverlay（`.mode{display:flex}`）与 #footRow（`.body{display:flex}`）——v1 页的模式占位层其实一直糊在主屏上。
- **修法**：两页 CSS reset 后各加一行全局守卫 `[hidden]{display:none!important}`（带注释说明根因）。这是兜底通解——今后任何元素只要挂 `hidden` 就一定藏得住。
- **验证**（InAppBrowser 实测，非仅理论推断）：用户激活的 strip 标签页刷新后 `getComputedStyle(#closedVeil).display==='none'`、`#mini` 同；长条窗正常显示（392×572），对话内容在；index.html 标签页刷新后 #modeOverlay / #footRow 均 `display:none`，主屏 `display:flex` 正常。curl 7105 两页 200 且响应含守卫规则。
- **注意**：用户在浏览器里开了 4 个 strip.html 标签页（同源同 URL），只刷新了激活的那个；其余旧标签页手动 F5 即效。

## 接手复核轮：两条「待查」查清 + 契约里一条旧结论被证伪（只读调查，正式代码零触碰）

- **为什么做**：§12-8 / guide §9-5 挂着两条"待查"（状态条三指标有没有数据源、内核有没有多 agent 编排能力），
  它们是拍板 v2.2 长条窗代价的前提。趁用户玩原型，先把底账查清，别让拍板建立在"大概要做不了"的猜测上。
- **怎么查**：只读 grep 内核运行时 `runtime/node_modules/@deepseek-ai/`（内核 0.2.0-rc.2），
  关键结论我自己逐条复核过（不是只转述子代理），没跑构建、没跑门禁、没改内核一行。
- **结论一：长条窗状态条三个指标内核全都有真数据源，不需要客户端造假、不需要改内核。**
  - token 速度：`sessionStats` 投影给 `decodeMs` / `decodeTokens`（也给了 `ttftMs` 首 token 延迟），
    官方 Web 聊天统计条的算法就是 `decodeTokens / (decodeMs / 1000)`
    （`dsh-session-stats/README.zh.md:44-47`、`dsh-client-ui-chat/lib/client.js:7004`）。
  - 缓存命中：`tokenUsage` 投影给 `uncachedInputTokens / cacheReadTokens / cacheWriteTokens`；
    **命中率本身不是现成字段**，官方 UI 也是现场算的（`formatCacheHitPercent`，
    `dsh-token-meter/lib/types/usage-projection.js:29-34`、`dsh-client-ui-chat/lib/client.js:6321`）→ 我们照同一口径算。
  - 上下文：`contextPressure{pressureTokens, projectedTokens, contextWindow}` + `contextBreakdown`，
    官方环形仪表 `ContextMeter` 用的就是它（`usage-projection.js:45-56`、`dsh-client-ui-conversation/lib/client.js:16998`）。
  - 统一入口：会话的 `projections` 快照 Store（`faceOf/get/values()`，
    `dsh-api-session-controller/lib/types/client/sessions/projection-store.js:31/41/57`）。
- **结论二：多 agent 统筹 = 内核给原语够，语义要工具台自己写（比预想乐观，但有明确代价）。**
  - 现成：多条会话并行收发（`remote.session.create`，每会话独立写锁，争用回 `session/writer-held`）；
    agent 预设注册与程序化建会话（`dsh-agent-preset-registry`；写作模式已经在用，
    `plugin/writing-mode/index.js:57-63` + `packages/mode-kit/src/harness/adapter.js:260-264`）。
  - 最贴近"主 agent 统筹"的现成品：实验包 `dsh-experimental-agent-team`（Lead 会话 + 成员信箱 +
    共享任务 DAG + `agentTeam` 实时投影，官方已有 UI 在读）。它**默认关闭**，靠 profile 开关启用 →
    **不破"内核零修改"**。
  - 代价四条：①实验包 README 明说不承诺稳定性；②启用 team profile 会**禁用普通 subagent 委派与全局
    child control**，与写作/GIR 现有工具集冲突，要回归；③它的拓扑是"一个 Lead 下面的一棵树"，
    与设想里"每个模式各自一条独立顶层会话"不一致；④内核**没有**跨顶层会话互发消息/派任务的服务，
    那条路只能插件自拼。统筹卡的"模式级任务"在内核里没有对应实体。

## 刀 3b：把"未证实"逼到底——列表行拿不到投影（实证）、改挂会话句柄，又抓出一个形状 bug
