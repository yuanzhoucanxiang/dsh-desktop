## 2. 应优先处理的问题

### F1 · P1：读取请求构造错误，打开文件与版本对比均受影响

位置：`plugin/writing-mode/client.js:452–455, 721–747, 1171–1179`。

`api()` 对整个 route 做 encodeURIComponent，调用方却传入 `get&path=...`。实际 URL 变为 `?route=get%26path%3D...`；host 解析到的 route 不是 `get`，也没有独立 path 参数。探针返回 `unknown-route`；相同文件用正确分离的参数返回 200 和原文。

加载失败时客户端没有明确报错，也不清除/锁定旧编辑缓冲；点击文件列表已经先更新 filePath。用户可能看到 B 的路径、A 的内容，继而把旧内容保存到 B。路由失败已复现；跨文件覆盖的整个 UI 操作链属于代码推导，未做浏览器 E2E。

**修复验收**：route 与 query 分离；失败不切换有效编辑文档；快速 A→B→C 时只采纳 C 的加载响应；逐一确认文件名、内容、保存目标一致；diff 确实读取两份目标文件。

### F2 · P1：保存回包会清掉新编辑的 dirty，退出也不保全待存内容

位置：`client.js:755–780, 815–839, 1694–1696`；`lib/store.js:264–268`。

persist 捕获发请求时的 content，响应成功后无条件 `setDirty(false)`。在请求期间继续输入时，旧响应仍可把新内容标成“已保存”，并导致新的自动保存计时器被 effect cleanup 取消。抽取生产回调、延迟 API 返回的探针复现：发送内容旧、编辑器内容新、dirty=false、状态 saved。

关闭写作模式会取消定时器；再次进入触发重新加载。没有退出前 flush、恢复草稿或 beforeunload 保护；也没有 mtime/hash 前置条件，不能识别主会话 Agent/外部编辑器对同一文件的修改。writeDoc 是直接覆盖写，没有采用仓库已有的原子持久化思路。崩溃损坏与多窗口冲突未做故障注入，不能声称已经发生。

**修复验收**：文档身份与编辑修订号绑定；旧保存回包只确认对应修订；单文件写入排队；切换、退出、刷新保护未保存内容；外部修改返回冲突；原子替换失败不损坏原文件。门禁失败也应允许保存草稿，避免为质量流程牺牲数据安全。

### F3 · P1：另存新版能覆盖已有版本，版本系列还会跨项目串联

位置：`client.js:657–677, 782–811, 1077–1104`；`lib/store.js:264–268`。

打开 v1 点 v+1，只计算成 v2，再调用普通覆盖保存。探针先建立已有 v2，调用后 v2 被替换，违反“保留旧稿”的产品承诺。历史稿没有只读保护，仍可普通编辑并自动保存。

versionSeries 扫描所有库/项目，仅按文件名匹配，没有限定项目和相对目录；不同项目同名章节会进入同一个系列。列表 maxVersionInGroup 更是取整个分组的最大 v，可能把尚无后续版本的另一章 v1 标为历史。后两项来自明确的代码路径，未做 UI E2E。

**修复验收**：host 按“项目+目录+作品单位”分组、寻找最大版本并独占创建；遇到同名返回冲突，不允许覆盖。历史修订采用明确操作。版本导航、列表徽标、diff、台账使用同一身份规则。

### F4 · P1：研究接口绕过库根限制；HTTP 边界还需补齐

位置：`index.js:250–262`；`lib/domain.js:193–200, 340–367`。

research/spark 直接将 body.path 交给 findProjectRoot，再读取 project/bible/outline；没有调用 resolveUnderRoots。隔离探针的库根外项目摘要标记被原样带回本地降级结果。真实 LLM 可用时，代码还会把该摘要放进模型请求；本次只用夹具验证读取，没有发送真实资料。

另外，host 只验证 remoteAddress，允许带外站 Origin 的 text/plain POST 写入夹具文件（返回 200）。当前内核 dsh-host-webserver 的命名 route 直接派发到 handler，没有给此插件自动加全局鉴权。此证据证明 handler 缺少来源验证；未模拟浏览器的本地网络权限机制，不把它表述成已完成的远程攻击。config/prefs 还会把 aiApiKey 明文返回客户端，和“客户端不持有 API Key”的策划表述不符。

**修复验收**：所有读取均经过同一受限 store，包括 AI 上下文和台账子文件的 realpath；补负向越界/junction 测试；写路由校验可信来源与请求类型，凭据读取只返回已配置状态。沿用内核可用的授权机制时必须实测覆盖本插件路由。

### F5 · P2：新建文稿落在库根，扫描树却不展示它

位置：`client.js:895–913`；`lib/store.js:189–224, 235–239`。

新建写入 `root/标题-时间戳.md`，树只展示含 project.md 的项目内部文件。普通库根下的新文稿真实存在、保存成功，但不在扫描结果中；探针已复现。UI 空态说“可打开任意 .md/.fountain”，对应路径打开能力也未在当前关键交互中落实。

**修复验收**：明确区分“新建项目”和“项目内新建章节/场”；或者完整支持散文稿区。保存后可再次从库中打开，重启不依赖 LS_FILE 才能找到。

### F6 · P2：门禁对象识别错误，而且已与契约、CLI 漂移

位置：`lib/domain.js:53–123`；`E:\剧本\验证\check-fountain.mjs`；CONTRACT.md。

- 所有 Markdown 都按小说章检查：world.md、project.md、outline、reviews 会因 1800–3200 字或缺钩子失败。探针已复现。
- Fountain 中 `"你好"` 通过全部检查，尽管契约声明 ASCII 引号=0。当前检测只匹配部分中文引号。
- CLI 识别 `#` 章节并复位对白状态，host 复制版没有该分支。一个夹具中 CLI 报“无对白”，host 却算两行对白并报“对白带引号”。两者结果口径已不同。
- 小说 checker 只认钩子前缀，不证明存在有效钩子内容、三段式标题完整或三轮评审完成。数值 PASS 不能解释为作品已放行。

**修复验收**：按项目形态与文档角色选择规则；共享单一规则实现和 schemaVersion；正例/反例一致；区分“机械检查通过”和“评审放行”。标准、阈值、适用载体应可配置。

### F7 · P2：台账的“当前稿”与版本契约不一致

位置：`lib/domain.js:126–190`。

当前稿取整个 draft 中 mtime 最新的文件，而不是作品单位的最高版本或登记的当前稿。触碰 v1 的修改时间后，已有 v2 仍被忽略，探针确认台账回到 v1。评审也按 mtime 选最新文件，没有和当前正文的版本/hash 绑定。角色状态与世界状态没有形成四本台账的一致性校验。

**修复验收**：稿件、钩子、评审统一绑定项目/单位/版本；正文变化后旧评审明确失效；台账更新有版本来源。不要把“最近改过的文件”显示为“当前稿”。

### F8 · P2：使用 Harness llm 不等于继承当前会话或 writing-studio

位置：`lib/domain.js:263–289, 300–338, 374–395`；`client.js:926–946, 1206–1235`。

没有传 sessionId。能访问 sessions 时倒序选最后创建且有请求头的会话；它不一定是用户当前会话。模拟两会话探针选中了无关会话。访问失败或没有记录则使用插件默认 provider/model；没有读取内核已有 agentDefaultModel.currentSelection()。Cordis 下 sessions 可见性尚未实测，不能承诺实际总能进入会话分支。

普通润色/续写调用只有通用 system prompt 和片段，没有 preset、角色状态、上一章钩子与项目写作纪律。research 才读一小部分设定。“发送到会话”只是预填当前 DOM 输入框并退出 overlay，没有验证其 preset/cwd，更没有自动评审闭环。

额外复现：LLM 返回两个 text block 时，block-end 用赋值覆盖累计内容，最终只保留第二段。没有请求取消/超时，输出也未绑定发起时的文档修订。AI 完成后切到另一文件仍可插入；“替换选区”在没有选区时替换整篇，这与按钮语义不符，且风险会被自动保存放大。

**修复验收**：模型路由使用明确会话或全局默认；显示实际模型来源；AI 请求绑定文件、选区、修订；取消和超时可恢复；多 block 不丢文；无选区不能默默替换整篇。明确“局部助手”与“writing-studio 工作流”各自保证什么。

## 3. 策划案与工作日志应怎样修订

### 3.1 交接状态不应只说“文档未提交”

接手时 `git status --short` 已有：WORKLOG.md、logs/2026-09-11.md、main.js、package.json、plugin/writing-mode/index.js 修改，以及未跟踪的 CONTRACT.md、lib/。**未提交内容含运行与打包代码。** 漏掉未跟踪文件时，别人仅提交已有修改会得到缺少依赖的 host。

策划案 §0/§2/§6/附录应分列：已发 v0.1.37、当前未提交源码、手工同步的安装目录、验证状态。〔129〕发布先于〔130〕分层；不能借前者证明后者的发布包验收。WORKLOG 索引 123–130 还漏了 131，属低优先级文档问题。

### 3.2 “三轮放行写死”只能说明提示词明确，不能说明工具强制

preset 的三轮规则确实存在（agent.cordis.yml:122–140），但没有相应 runtime 状态、轮次计数/审批事实、带稿件 hash 的评审记录 schema，也没有推进时的确定性校验。两个 checker 尚未成为 preset 的必经工具。历史验证 README 还记录了剧本曾跑到第 5 轮，后来通过改人设收口；本轮没有看到修改后再跑完整流程的自动化证据。

另外，人设同时存在“不覆盖旧稿/改写先复制”（38）和“小段修改不升版本”（146）；“全绿才放行”（135）和第三轮非阻塞黄可放行（138）；这些需要在契约里写成明确优先级和例外，不能由每个模型临场解释。

**正确目标**：保存草稿不受门禁阻拦；“定稿/推进下一单位”才验证必需检查、当前稿对应评审和批准事实。三轮限额应限制无休止自动修订，不能把时间用完解释为质量自动达标。

### 3.3 本地可用与可安装交付必须分开

当前 preset 位于用户目录 `~/.dsh/.agent-presets/writing-studio/`，checkers/runner 在 `E:\剧本\验证`，runner 还固定指向本机 Programs runtime 路径。仓库构建/内置接线中未找到 writing-studio 或 checkers 的分发接线。

因此“该机器有 preset + 桌面插件发布”不证明干净安装就能得到完整产品线。需要版本化保存 preset/checkers、契约版本、安装与升级策略，并在独立 DSH_HOME 中验收。仅独立 userData 的桌面预览仍共享账号/会话目录，不能替代干净安装测试。

### 3.4 产品范围宽，默认写作规则却过于单一

预设声称覆盖文学长篇、电影、舞台、短剧，但默认大量使用爽点、打脸、金手指、固定章长、三幕十五拍和必有对白/转场的校验。其风险是项目在表达目标上合格，却被统一规则判失败或被迫改形态。

这是策划层适配风险，不是本轮文学质量评分。建议把“形态/载体/目标平台/用户硬锁/选择的结构方法”先写进 project，再启用规则包；结构模型和风格建议默认是建议，不能自动升级为全项目硬性约束。

## 4. 可以保留的部分

- 文件系统存储、纯文本源文件、Agent 管流程/UI 管编辑的分工适合继续发展。
- store/domain/api 比原单文件 host 更易测，本次能直接调用 domain/store 做隔离探针就是收益。
- 模型出口复用 ctx.llm，避免维护第二套 provider 网络客户端，方向合理；需要补路由、上下文和流协议。
- 设置页、多根目录、版本入口、门禁摘要等已有实现，不必推翻重建。但目录分层不等于 Repository 契约已闭合：domain 仍直接读 fs，绕过 store 的权限校验就是实例。
- Release 资产和三方 client 字节证据真实；问题在功能验证和状态表述，不应否定已有代码工作。
