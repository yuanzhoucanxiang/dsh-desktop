## 1. W01 · P1：rename 到临时文件仍会暴露无锁空档

位置：`plugin/writing-mode/lib/project-memory.js:159–170`、`:186`。

回收者可能依据旧观测，把另一进程刚取得的活锁 rename 到临时文件。在读取移走的 token、决定还原之前，原锁路径已经不存在，第三个进程可以成功 open(wx)，进入临界区。事后的还原不能撤销第三个进程已经获得的执行权；还可能替换第三个进程的锁文件。

**真实进程复现：** A 观测到死进程的旧锁，在 rename 前暂停；B 回收旧锁并持新活锁读取 memory；A 继续 rename，原锁路径消失，此时 C 成功取得锁并读取同一 revision。继续 A 的 token 校验/还原，再让 C、B 依次提交。B/C 均成功返回 revision=2，最终只剩 base/holderB，holderC 的成功更新消失。A 自己最终返回 409，并不能保全 B/C 的数据。

证据：`review4-probes-results.json` W01。使用已退出子进程 PID 的临时锁 fixture；fs.renameSync/readFileSync 的前后屏障仅控制调度，生产锁与事务逻辑未替换。

**必须满足的条件：** 非持有者的回收操作不能把一个可能仍活跃的锁从公共锁路径移走后再确认。取得、回收及释放必须遵守同一套跨进程互斥协议。改用经过验证的跨进程锁机制，或建立所有竞争者都参与的可靠回收协调；不能用“先移走、发现不对再还原”作为互斥保证。若无法证明回收安全，应返回诊断并停止该次写入，而不是留下空档继续尝试。提交前所有权检查只能作为附加保护。

## 2. W02 · P1：队列虽串行，后续保存仍使用入队时的旧 baseRev

位置：`plugin/writing-mode/src/client/entry.js:91–114`；恢复采用 `:305–320`。

payload 在入队时构造并固定 baseRev。用户在第一次保存返回前继续输入，两次 payload 都是 baseRev=0；第一次写入后磁盘 rev=1，第二次必然 409。更严重的是，成功响应只有在当前 text/reference 与旧 payload 相同时才更新缓存 rev；有新输入时连已确认的服务端版本也不记录，后续编辑继续用旧版本。

**组件 + 真实 HTTP 复现：** 暂缓 FIRST_KEYSTROKE 的请求，输入 LATEST_KEYSTROKES；确认第二个请求没有提前发出，说明队列确实串行。释放第一次后，两个请求 baseRev 都为 0，响应依次 200/409，磁盘只有 FIRST_KEYSTROKE，界面仍显示最新文字；刷新后只恢复第一段。

恢复期间也存在相同的基线缺口：旧 checkpoint 为 rev=1，GET 尚未返回时用户输入新内容，保存发 baseRev=0 被拒绝；GET 返回后因为 recoveryGen 变化而完全放弃采用，包括 rev。再添加引用依旧发送 baseRev=0，继续 409。T02 的旧缓存覆写已避免，但新内容始终无法持久化。

证据：`review4-ui-results.json` 的两个 W02 场景。

**必须满足的条件：** 将“最新本地内容/编辑代次”和“服务端已经确认的 revision”分开维护。成功响应必须推进对应桶的已确认服务端版本，同时不能覆盖后来的本地内容。写入开始时，使用队列上一步确认的 revision，而非入队时捕获的旧值。恢复未完成前应暂缓发送持久化请求，保留本地编辑；恢复结果不覆盖新内容，但仍需要建立正确的服务端基线。不要把 409 当作队列正常推进；冲突、网络失败、重试和新 renderer 都要有明确恢复路径。

## 3. W03 · P1：清除删除版本记录，下一稿持续冲突，旧请求却可重新生效

位置：`lib/draft-checkpoints.js:57–62`、`:78–82`；客户端 `src/client/entry.js:108–114`、`:389–406`。

清除会删除文件并返回 rev+1，但下一次读取不存在的文件时 storedRev 又变为 0。客户端也只处理 data.checkpoint.rev，不记录清除响应里的 data.rev。发送成功后还会按相同旧 rev 排入两次清除，回调忽略错误。

**存储协议复现：** 保存 rev=1 → 清除返回 rev=2 → 用返回的 rev=2 保存下一稿却得到 409；反而一个清除前遗留的 baseRev=0 请求被接受，重新创建 rev=1。这既破坏后续保存，也重新允许已过期请求复活草稿。

**UI 复现：** 发送成功后界面清空；两次清除响应为 200/409；继续输入 NEW_THOUGHT_AFTER_SEND，保存再次 409，磁盘没有恢复副本。用户看到文字，不代表刷新后还能恢复。

证据：`review4-probes-results.json` W03、`review4-ui-results.json` W03。

**必须满足的条件：** 清除也是单调递增的版本变更，持久保留版本信息或等效墓碑，不能因删除正文而把协议版本归零。前后端统一处理保存/清除响应的 revision。发送后的文本、引用清理由同一次受保护状态转移生成正确快照，避免两个同版本请求相互冲突；保留发送期间的新输入/新引用，并反馈清除失败。旧 baseRev=0 在清除后也必须被拒绝。
