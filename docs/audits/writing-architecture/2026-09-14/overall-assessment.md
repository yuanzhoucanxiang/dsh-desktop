## 4. 影响实际使用的关键缺口

### 4.1 前端仍高度耦合，会话协调不能被草稿版本测试代替

`src/client/entry.js` 同时负责会话创建、原生节点转换、组件、请求和保存状态。将旧文件搬入 src、再拼回产物，完成了源码/产物区分，但没有完成方案的 feature 与 adapter 边界。

`ensureCompanionSession` 仍按读关联 → 建工作区/会话 → 写关联执行，没有方案要求的共享创建 Promise 或 host 绑定预留协议。此前通过的跨进程存储互斥针对备忘/checkpoint，不证明跨窗口首次会话创建也有幂等保证。H01/H02/H06/H07 应作为适配层建设与验收重点。本次没有把未测试的会话竞态写成已经复现的丢数据事件。

### 4.2 陪伴体验需要可查看、可修正的项目连续性

当前预设明确允许自然讨论、试探、改口和按需工具使用，没有每轮阶段、评分、字数配额或强制流水线；这一方向符合用户要求。Harness 的模型、工具、权限和完整会话入口得到保留。

不足集中在作者如何理解和修正记忆：备忘面板支持的操作仍偏基础，尚未形成“讨论中提出候选 → 作者确认 → 修改/撤回 → 下轮使用新状态”的完整 UI。应优先补这个闭环，不增加每轮必须填写的卡片或审批。

自然度、长对话连续性以及讨论转执行的效果仍没有真实模型证据，不能由预设文字与 fixture 测试推断已经达标。

### 4.3 上下文透明度确有未接通的代码

发送端传入 `memoryRevision`，但 `src/shared/context-builder.js` 没有把它写入返回对象。本次直接调用传入 revision=7，返回对象确实没有该版本。

同模块定义了 `memoryHint`，入口中没有调用；当前也没有本次发送的备忘参考开关/展开列表。故“已把备忘拼进消息”可以确认，“作者能查看本轮采用了哪份备忘并选择不用”尚未完成。优先补版本、选中条目与开关，继续保持不限制普通聊天长度/轮数。

### 4.4 契约与验收文档需要同步真实实现

`CONTRACT.md` 仍称未发送引用仅在当前页面保存、不承诺刷新恢复；API 表没有新 memory/draft 路由及其 schema/版本/错误语义。其内容已落后于实际通过的实现，应更新为准确的交接契约。

最新 `acceptance-arch-pack.md` 明确承认 feature/adapter/备忘 UI/30 项/真实模型未完成，未伪称全部通过。这一边界应保留。32 条审查时序也不能替代方案的 30 个验收 ID。
