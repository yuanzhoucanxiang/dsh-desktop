## 3. 返工项

### R01 · P1：普通恢复没有把正文/引用同步进共享缓存，移除引用会清空磁盘正文

位置：`plugin/writing-mode/src/client/entry.js:323–338`，重点是 327 行只推进缓存 rev，330–337 行只恢复界面/原生输入。

恢复成功后，界面显示 checkpoint 正文和引用，但 `companionDrafts` 仍可能是 `{ text: '', reference: null, rev: N }`。随后移除引用会从这份空正文缓存发起保存，写入清除墓碑。此时输入框仍有文字，持久恢复副本却已被清空。

实测：已有 `NEW_DURING_RECOVERY` 和选区引用，正常刷新并等待恢复，点击「移除稿件引用」。磁盘成为 `text: '' / reference: null / rev: 8 / cleared: true`，输入框仍显示原文。没有要求用户改动正文。

修订要求：在恢复代数仍有效时，对 UI、原生草稿和缓存采用同一份完整有效快照；原生已有文字的优先级也应进入缓存，不能只把服务器 rev 拼到空正文上。引用单独增删必须保留当前有效正文。

### R02 · P2：恢复期间主动清空被当作“没有内容”，旧稿刷新后复活

位置：`plugin/writing-mode/src/client/entry.js:340–345`，尤其 343 行用 `cached.text || cached.reference` 决定是否 flush。

实测：磁盘已有 `OLD_TO_REMOVE`，延迟恢复 GET；用户输入 `TEMP_THOUGHT` 后清空；再放行 GET。可见输入正确保持空，但没有发出清除 POST。再次刷新，旧的 `OLD_TO_REMOVE` 回到输入框。

修订要求：用 dirty 标记或编辑代数记录恢复期间是否发生修改，空字符串和空引用也属于需要保存的状态。主动清空应提交带正确 baseRev 的墓碑；未经编辑的初始空状态则不能误清掉服务器草稿。

### R03 · P1：409 后只刷新 rev，队列下一项自动覆盖另一写入者的新稿

位置：`plugin/writing-mode/src/client/entry.js:104–135`，重点为 124–129 行冲突后只把服务器 rev 写回本地缓存。

实测时序：

1. 延迟 `LOCAL_BEFORE_CONFLICT` 的第一个 POST。
2. 输入 `LOCAL_QUEUED_BEFORE_REMOTE`，形成第二个待执行保存。
3. 同一项目、同一 window bucket 的独立写入者保存 `NEWER_OTHER_WRITER`，推进到 rev=10。
4. 放行第一个 POST，因旧版本返回 409。
5. 客户端 GET 服务器版本，给未解决冲突的本地内容换上新 rev；已经排队的第二次保存随即 200，磁盘成为 `LOCAL_QUEUED_BEFORE_REMOTE`。

两次本地编辑均发生在另一写入者提交之前。冲突后没有新作者编辑或选择，却自动覆盖了另一份新稿。错误提示可能出现；问题是提示没有阻止后续覆盖，不是声称界面完全没有报错。

边界：这是对**同一 bucket 存在第二写入者**的受控竞争验证，不代表普通不同 windowId 的窗口天然共用文件。版本冲突协议必须对其本来要拒绝的同桶竞争保留保护。

修订要求：发生真实版本冲突后暂停该 bucket 的自动保存队列，保存本地与远端快照，提供明确恢复/合并/重试路径。读取新 rev 不能等价于冲突已经解决，不能自动重新授权冲突前排队的完整快照覆盖远端。该选择只需用于冲突恢复，不应限制正常聊天流程。
