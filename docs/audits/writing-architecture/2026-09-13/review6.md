## 3. 返工项

### S01 · P1：已有会话“采用远端”未同步原生输入，下一次发送仍发旧本地文字

位置：`plugin/writing-mode/src/client/entry.js:526–533`；输入来源见 364 行。

已有会话时，输入框的 `draft` 来自 `info.hooks.input`。远端选择只调用 `setLocalDraft` 和 `setReference`，没有调用原生 `inputActions.setDraft`。缓存/磁盘采用了远端，真正显示和发送的原生草稿却保持本地内容。

实测：同一 bucket 的本地 `BOUND_LOCAL` 与远端 `BOUND_REMOTE` 冲突，点击「采用远端」。磁盘为 `BOUND_REMOTE`，输入框仍是 `BOUND_LOCAL`；直接点击发送，实际交给 prompt 的 content 为 `[{type:'text',text:'BOUND_LOCAL'}]`。测试只捕获协议调用，无模型回合。

修订：通过统一的草稿采纳动作同步当前有效输入来源、缓存和引用；存在会话时必须更新原生输入。验收同时检查输入框、原生 store、缓存/磁盘及实际准备发送的内容，不能只断言磁盘换成远端。

### S02 · P2：恢复完成后的自动保存冲突，没有触发界面状态更新

位置：`plugin/writing-mode/src/client/entry.js:400–403`，以及 171–179、517 行。

恢复结束以 `persistCompanionDraft(project)` 保存 dirty 内容，没有传状态回调。409 后只修改普通 Map；界面不是该 Map 的订阅者，若没有其他 React 状态更新，就不会显示冲突操作区，也没有保存失败提示。

实测：延迟恢复 GET，在等待期间输入 `LOCAL_PENDING`；独立写入者在同桶保存 `REMOTE_AFTER_GET`；放行旧 GET 后自动 flush 返回 409。自动保存实际暂停，输入框仍为 `LOCAL_PENDING`，磁盘为 `REMOTE_AFTER_GET`，但页面没有「采用远端」按钮。后续输入等操作可能间接触发提示，所以不是声称永远无法恢复；问题是发生故障时没有及时呈现真实保存状态。

修订：把恢复、保存、冲突和失败状态作为可订阅状态统一发布，不依赖某个事件处理器是否传了可选回调。恢复 flush、手工解决、普通编辑都应消费同一状态；413/网络失败也要显示失败并保留未保存内容。dirty 不应在实际保存成功之前无条件抹掉。

### S03 · P1：读取远端失败时仍允许“采用远端”，默认空快照清掉本地输入

位置：`plugin/writing-mode/src/client/entry.js:159–176`、110–120、526–533 行。

冲突后读取远端失败时，代码仍创建 `remoteRev: null / remoteText: '' / remoteReference: null` 的“快照”，随后照常启用「采用远端」。未知状态与确认的空草稿混为一谈。

实测：无会话页面中，本地 `LOCAL_MUST_SURVIVE_FAILED_READ` 与远端 `REMOTE_VALID` 竞争；首个 POST 409，拦截其后那一次远端 GET 返回 503。界面仍出现「采用远端」。点击后可见本地输入变为空；用旧 rev 保存空内容再次 409，磁盘仍为 `REMOTE_VALID`。本地输入已在没有有效远端快照、也没有成功保存的情况下被丢弃。

修订：区分远端快照 loading / valid / failed；只有有效快照及版本才能采用。读取失败时保留本地文字/引用和冲突状态，提供重试；不能用空值表示读取失败。解决失败应仍可恢复两边的有效内容，不提前删除冲突信息。与本轮其他并发场景一样，该探针针对同一 project/window bucket，不指普通不同 windowId 的窗口会串文件。
