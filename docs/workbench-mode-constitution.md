# 工作台兼容改造宪法（模式 ↔ 创作工作台）

> 命名说明：本文 2026-10-18 起用「工作台」（与策划案口径一致）；**代码、UI 文案与设置段 id 仍是
> 「工具台」/`workbench`**，改名顺序与代价见 `docs/workbench-mode-plan.md` §12。正文里出现的「工具台」
> 与「工作台」指同一件事，历史条文不改写（只增不改）。

> **这是什么**：一个模式（写作、GIR 生图、以后任何模式）要"能被工作台接纳"必须遵守的**条文**。
> **给谁看**：新加一个模式的作者、改造老模式的作者、以及审阅这些改造的人。
> **怎么用**：写代码前**通读一遍**；收工前照最后一节的**适配清单**逐条打勾。
> **效力**：契约字段的**单一事实源**是 `plugin/workbench/README.md` §一（模式契约）；
> **用户体验与交互口径**的单一事实源是 `docs/workbench-mode-plan.md`（策划案 v2）；本文写的是**改造规则与纪律**。
> 与前者冲突时以 README 的字段定义为准，与后者冲突时以策划案为准，并回来修本文。
> **版本**：v1.1（2026-10-13 制定，起草时把写作模式已跑通的实践全部收进来；2026-10-18 补全指针与"已知边界"清理；
> 配套实现见 `plugin/writing-mode`）。

## 一、总则

**第一条（可选接入，绝不强绑）**　模式**必须**在没有工具台时照常可用：不带工具台的官方壳、老安装包、
被禁用的工具台，都是正常工况。
*为什么*：工具台是"门面"不是"地基"；一条把模式绑死在自己壳上的路径，会在别人的环境里直接不可用。
*怎么做*：`ctx.inject(['workbench'], …)` 是可选的；拿不到服务就保持自持入口（见第二条）。
指针：`plugin/writing-mode/src/client/adapters/workbench-bridge.js`（桥接层不 import React、可在 node 里单测）。

**第二条（入口唯一）**　工具台在场时，模式**必须**让出自己那套重复入口（侧栏按钮、浮钮、设置页里的开关），
让人只有一个"从哪进"的答案。
*为什么*：两套入口同时存在时，用户看到的是"两个都像能进"，实际状态还可能分叉。
*怎么做*：模式订阅 `hasWorkbench()` / `subscribeWorkbench()`，在场就渲染 `null`。
**注意时机**（2026-10-13 实机踩到）：`ctx.inject(['workbench'], …)` 是**异步**的——在 `apply()` 里紧接着问
`hasWorkbench()` 多半还是 `false`，于是浮钮照样注入。**要改成"绑定成功之后再隐藏/移除"**，
或者用 `subscribeWorkbench()` 订阅；别在 entry 阶段同步判断。

**第三条（注册即声明，不反向索取）**　模式**只能**通过 `registerMode(descriptor)` 描述自己；
**禁止**跨插件 import、**禁止**去读工具台的内部状态、**禁止**要求工具台"替我干某件事"。
*为什么*：视图是**运行时传进来的组件引用**，契约字段是唯一界面；越过它的耦合会在任一方升级时炸。
*怎么做*：需要的都放进 descriptor（见第四条）。

**第四条（视图三件套，按用途给，别多给）**　模式可以交三种视图，**用途不同、不要混用**：

| 字段 | 给谁用 | 形态 |
|---|---|---|
| `tile: { label, view }` | 工具台**宽窗主屏**右侧的"内容窗口" | 运行时组件引用 |
| `dock: { label, view }` | **别人当主视图**时，工具台右缘那块"轻视图"（顺眼看一下） | 运行时组件引用 |
| `splice: { label, mount?, view?, width?, assistant? }` | 被**拼到长条旁边**时的**完整界面** | 见第五条 |

*为什么*：`dock` 是"看一眼"，`splice` 是"在这干活"，两者混用会让用户以为自己在干活、实际只有只读视图。

## 二、渲染与窗口

**第五条（单实例走 mount，可重挂走 view）**　模式的界面若是**单实例**（有自己的 React 根、编辑会话、
按窗口分桶的草稿恢复——写作台就是），**必须**交 `splice.mount(container)`：把自己的界面**渲染进**
工具台给的容器（`createPortal` 或挂 DOM 都可以），并返回一个 dispose。
无状态、可自由重挂的模式才用 `splice.view`。
*为什么*：挂第二份会和本体抢同一个文件/同一份草稿（写作模式坞视图的头注里写着这条教训）；
而**不要**用"把 DOM 搬过去"的办法——React 17+ 的事件委托挂在根容器上，挪出那棵树事件就哑了。
*怎么做*：宿主用一个小 store 记住容器（`plugin/writing-mode/src/client/state/splice-host.js`），
界面组件订阅它、决定"portal 进去"还是"自己整屏渲染"。

**第五条之二（拆成多窗口后：现场只读共享）**　一个模式被拆到**多块窗口**（如写作台 + 它的助手对话）时，
**必须**让"有编辑权的那个窗口"把**只读现场摘要**广播给其它窗口（`BroadcastChannel` 等同源通道），
其它窗口**只消费、不写**。
*为什么*：不同窗口 = 不同 JS 上下文，各存一份状态会让"助手看不到你正在写什么"（写作模式 2026-10-13
实报，plan §0.2 G1/G2）；而**跨窗口写**必然出现两份草稿互相覆盖——比"看不到"更糟。
*怎么做*：`plugin/writing-mode/src/client/state/live-share.js`——按 URL 片段分角色（`desk` 发布 /
`assistant` 订阅 / `overlay` 自成一体）、400ms 节流、`hello` 握手补发当前现场、无通道时安静降级；
界面上如实注明"来自写作台窗口"，不假装是本窗口的稿。

**第六条（模块窗口必须自报家门）**　工具台可以把一个模式开成**独立窗口**：窗口加载的是同一个内核页，
URL 片段写明 `#dsh-wb-module=<modeId>[&kind=assistant]`。
模式的页面**必须**认领这个片段：`kind=main`（或缺省）渲染**本模式的完整界面**，
`kind=assistant` 渲染**本模式的助手对话**。
*为什么*：不认领的话，模块窗口里显示的是内核默认界面（实机截图里出现过"探索未至之境"欢迎页——
用户的第一反应是"这窗口是坏的"）。
*怎么做*：读 `location.hash` 认 `modeId`；认领之后**不受**"是否激活"的门槛限制（模块窗口里模式本来就没激活）。

**第六条之二（模块窗口要自带出口——2026-10-18 补）**　模式在模块窗口里**必须**给用户一个
**真正的关闭/收起路径**（关窗、或退回拼合、或明确标注"关闭请用接缝再点一次"）。
**禁止**只提供一个"失活"按钮就当作关闭——模块窗口里失活不会让界面消失。
*为什么*：模块窗口的门槛是 `!active && !spliceHost && !isModuleWindow`，`isModuleWindow` 让它**永远渲染**；
写作台顶栏那个「退出」只是 `setModeActive(false)` ⇒ 在模块窗里点了**界面纹丝不动**（策划案 §9.1 的 D2，
2026-10-18 体检确认）。而模块窗是无边框的、`shell:close-window` 只关主窗 ⇒ 用户也点不到系统关闭钮（D3）。
*怎么做*：模块窗里把"退出"的文案与动作改成"关闭这块窗口"（经壳的模块窗口通道），或至少在按钮上写明
"这是回到写作台，不是关窗"。

**第七条（宽度自己报，几何别伸手）**　模式**可以**用 `splice.width` 声明"我这块想要多宽"；
**禁止**索取任何绝对坐标。工具台只发**档位与有界标量**给壳，位置/尺寸/贴边全由壳算。
*为什么*：窗口边界、屏幕尺寸、多屏缩放都是壳才知道的事；模式自己算必然在别人的机器上出错。
*怎么做*：写作台声明 720（三栏界面在 420 里会被裁）；壳会按工作区把它夹住，放不下就缩。

**第八条（窗口宽度不是模式的假设）**　模式的界面**应当**在窄容器里也能用（`dock` 视图尤其），
并**应当**在 `splice.width` 里报出自己需要的最小可用宽度。
*为什么*：长条只有 420 宽；把宽窗布局硬塞进去就是"破版"，而破版会被当成"工具台坏了"。

## 三、状态与协作

**第九条（关闭守卫先问模式）**　工具台在切走/退出/交接前**必须**调用模式的 `canDeactivate({to, reason})`；
模式**必须**如实回答（有未保存内容就拒绝），**禁止**在守卫里做副作用。
*为什么*：L1.5 的拍板——守卫只回答"能不能"，落状态由 `onDeactivate` 负责。

**第十条（模式自持的开关要报账）**　模式自己开的/关的（热键、设置页、浮钮）**必须**通知工具台
（`setActive(id, 'mode-local')` / 主动 `setActive(null, …)`）。
*为什么*：否则两套状态分叉：工具台以为模式在、模式以为自己关了。

**第十一条（上下文只报事实）**　`context.get/subscribe` 报"现在在做什么"（作品/章节/产物），
工具台只**汇总与展示**、不解释内容；模式报不出来就返回 `null`，**禁止**编造。
*为什么*：这条是 L1 的验收基础，入口上的"正在做"靠它。

**第十二条（交接待客要诚实）**　收到交接的模式**必须**在 `onHandoff` 里真处理；
没有这个钩子的模式，工具台**必须**如实标 `delivered:false`。
*为什么*：假装送到了比重发一次更贵——用户会以为对方已经收到。

## 四、门禁与文档

**第十三条（模式自带门禁，且要覆盖契约）**　模式仓库**必须**有：构建一致性门禁、自己的测试套件、
**至少一条针对工具台适配的测试**（注册描述长什么样、mount/dispose 语义、认领片段的判定……）。
*为什么*：契约是"对外的脸"，它变坏时模式自己最先能发现。
*参考*：`plugin/writing-mode/test/writing-splice.mjs`（3 组：宿主 store / mount 的 dispose 语义 / 注册描述）。

**第十四条（外壳侧 e2e 留在外壳仓库）**　需要**外壳运行时**的端到端门禁（真窗口、真形态、真拼接）
留在 `dsh-desktop/scripts/verify-*`；模式仓库只管 node 层。
*为什么*：拆库时的既有约定（见 `AGENTS.md` 的仓库边界），路径不变、照旧跑。

**第十五条（文档三件套）**　每次改造：模式仓库的 `logs/`+`CHANGELOG.md`+`WORKLOG.md` 索引，
以及外壳侧 `plugin/workbench/README.md` §一（如果动了契约）、`docs/workbench-mode-plan.md`（如果动了
用户可见的行为/参数/文案）与本文末尾的现状对照表（如果动了能力）。
*为什么*：见 `AGENTS.md` §2.1——"下一位协作者只看文档，能不能复原你今天做的事"。

## 四之二、外部工具型模式（Blender / ComfyUI 这一类）

> **适用范围**：模式背后是一个**不在 dsh 进程里的外部工具**（Blender 的 CLI/后台、ComfyUI 的 `:8188` 服务、
> 将来的视频/音频工具）。写作模式那种纯前端模式**不适用本章**，给了字段反而多余。
>
> **为什么单开一章**（2026-10-18 补）：第一～十五条是按"模式 = 一块前端 UI + 内核会话"写的，
> 写作与 GIR 都是这个形状。但外部工具型模式多出四件事——**后端可能没起来**、**任务跑很久**、
> **产物在磁盘上**、**可能抢 GPU/端口**——前三条原来一条契约字段都没有
> （`health` 归一到 mode 记录里但 `publicView` 不暴露、注册表没有 `healthOf`，
> `job/progress/cancel` 与 `artifacts.*` 在注册表里查到 0 处）。**不补这一章，接 Blender 时必然重演
> G9/G10 那类"点了没反应"。**
> **编号说明**：条文用 16–20（接在第十五条之后），章节排在"四、门禁与文档"之后——
> 因为它们**不是**"通用接入纪律"，而是**一类模式的专用纪律**；读的时候先过完前十五条再来。


**第十六条（后端状态必须可见，且 `probe` 必须有界）**　模式若依赖外部后端，**必须**实现
`runtime.probe()`：**3 秒内**返回，**绝不抛**，返回 `{ state, detail, version }`，
`state` 取 `ready | starting | down | error`。
*为什么*："装了但后端没起"是最常见的工况。没有这一条，用户点进去看到一片空白，
而工作台以为它"就绪"——正是 G9/G10 的同款失败（禁用/静默 = 点了没反应）。
*怎么做*：照 GIR 的 `/health` 指纹判定（`E:\GIR\gir-dsh\dsh-plugins\gir-ui\index.js:114-133`：
3 秒超时、必须 200、必须是 JSON、必须匹配 `{status:'ok', service:'...'}`），
**只认指纹、不认"端口有人应答"**——否则任意本机服务都能被当成后端。

**第十七条（不可用要给整块说明 + 一条出路）**　`state !== 'ready'` 时，模式的完整界面与接缝标记
**必须**显示：**现在是什么状态** + **为什么** + **一条可执行的下一步**
（"启动 Blender" / "去设置里填地址" / "先打开 ComfyUI"）。
*为什么*：与 UI/UX 规范的空状态条款同源——空状态 = 解释"现在没有什么" + **一个可执行动作**。

**第十八条（工作台不代管外部进程）**　工作台**不 spawn、不 kill、不重启**任何外部工具；
需要"一键启动"的模式**自己**实现 `runtime.start()`，工作台只调用并**如实回报结果**。
外部工具的端口、路径、凭据**一律存在模式自己的配置里**，不进 `workbench.json`。
*为什么*：R5 已定——工具台无法代管其生命周期（GIR 后端就是先例）。
把进程管理收进门面会让"工作台崩了，Blender 也被带走"这种事故变成可能。
*反例*：`shell:notify-command` 那种 `spawn(任意命令串)` 的通道**绝不许**为这件事新开——
壳层加固审计的第一条威胁模型就是"内核页面能调 IPC 是要紧的"。

**第十九条（长任务要有队列与取消，且取消必须是真的）**　有长任务的模式**必须**实现
`jobs.list()`（含 `progress` 与 `state`）；能取消就实现 `jobs.cancel(id)`，
**不能取消就不要实现它**——UI 据此不显示取消钮，而不是显示一个点不动的按钮（G9 的教训）。
*为什么*：Blender 渲染、ComfyUI 队列都是分钟级；用户需要知道"还剩多久""能不能停"。
"点了没反应"的取消钮比没有取消钮更糟。

**第二十条（产物走 artifacts，路径不出模式）**　模式产出的东西**必须**通过
`artifacts.list()` 报**句柄**：`{ mode, kind, id, path?, title, at }`；
工作台只做"列出 + 点一下跳回"，**不解释、不搬动、不复制**产物文件。
*为什么*：与 §5.4"跨模式引用"同一条逻辑——引用一旦深耦合，两个模式的版本与删除语义都要联动。
GIR 的图归 GIR 的库，写作的稿归写作的库；工作台只给一个"最近产物"的入口。

**第二十条之二（外部 Web UI 不内嵌——2026-10-18 拍板 A）**　模式的界面**必须**是**自己用
`--dsw-*` 令牌画的原生前端**，**禁止**指望把外部工具的 Web UI（ComfyUI 的节点编辑器、
Blender 的 web 面板）内嵌进工作台。
*为什么*：`moduleWindowUrl()` 只能拼 `kernelPageUrl + #hash`，模块窗口加载的是**内核页**；
`hardenWindow` 的 `will-navigate` 只放行内核页 URL，其它 `http` 一律 `openExternal` 丢给系统浏览器
（`main.js` 的 `hardenWindow`）。要内嵌就得新增壳能力 + 定 CSP/凭据边界，**这轮明确不做**。
*代价要说清*：ComfyUI 的节点工作流几乎不可能用原生前端重画——所以对 ComfyUI 的合理形态是
**"工作台只当任务台"**：选工作流模板 → 填参数 → 排队 → 看进度 → 收图；
要拖节点请**点一下用系统浏览器打开 ComfyUI 自己的界面**（`artifacts`/`runtime` 里给那条外链）。

## 五、新模式的适配清单（照抄即用）

1. **桥接层**：新建 / 复用"可选服务"适配层（`inject(['workbench'])` 拿不到就降级），**不 import React**，可在 node 里单测；
2. **让出重复入口**：订阅 `hasWorkbench()`，在场时自持入口渲染 `null`（第二条）；
3. **注册描述**：`id` / `label`(函数，延迟取文案) / `order` / `mount` / `canDeactivate` / `onActivate` / `onDeactivate` / `context`；（第三条）
4. **主屏内容窗口**：有内容视图就给 `tile`；没有就别给（工具台会退化为"进入"按钮卡）；
5. **轻视图**：别人当主视图时值得看的那点东西给 `dock`（只读、极小）；
6. **完整界面**：`splice.mount(container)`（单实例模式）或 `splice.view`（可重挂），并**声明 `splice.width`**；（第五、七条）
7. **认领模块窗口**：读 `location.hash` 的 `dsh-wb-module=<你的 id>` 与 `kind`，渲染对应界面；（第六条）
8. **接管模式开关**：热键/设置页/浮钮的状态变化都要 `setActive(id, 'mode-local')` 报账；（第十条）
9. **上下文**：`context.get/subscribe` 报事实、报不出返回 `null`；（第十一条）
10. **交接**：需要就实现 `onHandoff`；不需要就别实现（工具台会如实标未送达）；（第十二条）
11. **测试**：至少一条契约测试（注册描述 + mount/dispose + 认领判定）+ 构建一致性门禁；（第十三条）
12. **文档**：模式仓库 logs/CHANGELOG/WORKLOG + 本宪法末尾的"现状对照表"若你改了能力就同步它。（第十五条）

> **若你的模式背后有外部工具（Blender / ComfyUI 这类），再加这五步**：

13. **后端探测**：实现 `runtime.probe()`——3 秒内返回、绝不抛、只认指纹不认端口；（第十六条）
14. **不可用界面**：`down/starting/error` 时给整块说明 + 一条可执行出路（启动/去设置/先开工具）；（第十七条）
15. **启动归你**：要"一键启动"就自己实现 `runtime.start()`；**不要**指望工作台代管进程，
    端口/路径/凭据存你自己的配置，不进 `workbench.json`；（第十八条）
16. **长任务**：`jobs.list()` 报 `progress` 与 `state`；能取消才实现 `jobs.cancel()`，不能就别实现；（第十九条）
17. **产物**：`artifacts.list()` 报句柄（`{mode,kind,id,path?,title,at}`）+ `artifacts.open()` 跳回；
    **界面必须自己用 `--dsw-*` 画**，不内嵌外部 Web UI（要拖 ComfyUI 节点就外链系统浏览器）。（第二十、二十条之二）

### 助手窗口（`splice.assistant`）的现状（2026-10-13 补齐，同日更新）

- 写作模式声明 `splice.assistant = { width: 360 }` ⇒ 拼接时工具台**同时开两块**：主界面（右）+ 助手（左）；
- **左侧空间是有限的**：长条左边常常只剩一百多像素 ⇒ 壳给助手窗一个**独立下限 160**，
  宁可窄也不许压在长条上（实机曾重叠 40px）；
- 助手窗口里写作模式**认领片段**（第六条）并**只渲染写作伙伴面板**：
  `.is-assistantWindow` 收掉顶栏与 `.dshWmBody` 里除 AI 侧栏之外的同级，AI 侧栏铺满。
  **结构是量出来的**（`.dshWmRoot > [.dshWmBar, .dshWmBody]`，AI 侧栏在 `.dshWmBody` **里面**）——
  第一版按猜的写 `>*:not(.dshWmSide)`，把装着侧栏的 `.dshWmBody` 一起收掉 ⇒ 助手窗口**整块空白**。
  实测：`.dshWmBody` 361×602 铺满，可见块只剩 `dshWmCompanion*` ✓。

## 七、已知边界（别当成已有）

- **主窗与模块窗已经都无边框**（2026-10-13 完成：`frame:false` + `titleBarOverlay` + 顶部拖拽带；
  模块窗 `frame:false / hasShadow:false / resizable:false`）。剩下的**不是边框**，而是
  **负缝 -8px 的几何对齐**：跨屏缩放不同时仍可能差几个像素（实测请求 420×601 得 481×688，
  比例正好是 312/273）⇒ 窗口必须**在目标屏上直接创建**。
- **多屏缩放**：同上。跨屏 `setBounds` 会被系统按目标屏再缩放一次。
- **三块的宽度是"抢来的"**：长条宽固定（420），助手与主界面按各自剩余空间缩；屏幕太窄时先缩主界面、
  再到助手下限 160 —— 再不够就只能重叠（当前实现不处理这种极端情况）。
- **吸附阈值 32px / 宽限 240ms 是拍的值**：32 是 2026-10-18 从 48 调下来的（反馈"不够黏"），
  **仍是手感旋钮**，等上手摸过再定稿（命名常量，改一个数即可；hardening 只校验 16–64 区间）。
- **助手窗口的现场是只读的**：能看、能说，编辑权只在写作台那块窗口（宪法第五条之二）。
  "端到端实测（写作台开稿 → 助手窗口同步）"截至 2026-10-18 **仍待人眼确认**。
- **`runtime` / `jobs` / `artifacts` 只是契约设计，工作台侧尚未实现**（2026-10-18）：
  注册表还不收这三个字段（`normalizeMode` 只认到 `dock/tile/splice/onHandoff`），
  `publicView` 也不暴露 `health`（`registry.js:107` 那几个 `hasXxx` 里没有它），
  接缝上更没有任何"后端未就绪"的标记。**第一个外部工具型模式（Blender/ComfyUI）落地时，
  这三件事要一起做**：① 注册表收字段 + `healthOf/jobsOf/artifactsOf` 三个读口；
  ② 接缝与瓷砖显示后端状态与任务进度；③ 探针加对应判据（真起一个假后端验 `down → ready → down`）。
- **外部 Web UI 不内嵌**（第二十条之二，2026-10-18 拍板 A）：`moduleWindowUrl()` 只拼内核页，
  `hardenWindow` 把非内核 `http` 一律甩给系统浏览器。要内嵌必须新增壳能力并重定 CSP/凭据边界，**本轮不做**。
- **三条已确认但未修的缺陷（2026-10-18 体检，代码另开一轮）**——写在这里是为了让**写模式的人**知道
  当前的真实交互，别照着"应该有"去设计：
  ① **置顶开关没有入口**：`setWorkbenchStripOnTop` 在 preload 上，门面零调用、设置窗口也没有它；
  ② **模块窗口里点模式的「退出」界面不变**：模块窗的渲染门槛把 `isModuleWindow` 排除了，
  失活不等于消失——**模式作者在模块窗里要自己给一个真正的关闭路径**；
  ③ **分离出去的模块窗口没有窗口内关闭钮**：无边框无 `titleBarOverlay`，`shell:close-window` 只关主窗。
  完整影响与证据见策划案 §9.1（D1/D2/D3）。
